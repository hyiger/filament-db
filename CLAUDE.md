# Filament DB

Next.js 16 + Electron desktop app for managing 3D printing filament profiles with NFC tag support.

## Commands

```bash
npm run dev              # Next.js dev server (localhost:3456)
npm run build            # Production build
npm run lint             # ESLint
npm test                 # Vitest (single run)
npm run test:watch       # Vitest (watch mode)
npm run test:coverage    # Vitest with coverage
npm run electron:dev     # Electron + Next.js dev
npm run electron:build   # Full Electron build pipeline
```

## Architecture

- **Frontend**: Next.js App Router (TypeScript, React 19, Tailwind CSS)
- **Backend**: Next.js API routes under `src/app/api/`
- **Desktop**: Electron with esbuild-compiled main/preload (`electron/`)
- **Database**: Mongoose ODM with MongoDB Atlas (cloud), embedded MongoDB (offline), or hybrid mode
- **Tests**: Vitest with mongodb-memory-server; coverage enforced on `src/lib/` and `src/models/`
- **NFC**: @pokusew/pcsclite (native module, requires PC/SC headers on Linux; imported directly in `electron/nfc-service.ts`). Reads OpenPrintTag (NFC-V/ISO 15693), OpenTag3D (NTAG213/215/216, ISO 14443-3A Type 2; write supported — see the "OpenTag3D read support (#864)" section), and Bambu Lab MIFARE Classic (ISO 14443-3A) tags

## Key Conventions

- **Path alias**: `@/` maps to `src/`
- **tsconfig excludes**: `node_modules`, `electron/`, `scripts/`, `packages/` (scripts use native modules unavailable in CI; `packages/` is the standalone Expo mobile app with its own toolchain)
- **Standalone output**: Next.js builds in standalone mode for Electron bundling
- **Dark mode**: Use `dark:` Tailwind variants on all UI — app supports both light and dark themes. Native controls (the `<select>` option popup, scrollbars, date/color pickers) follow the CSS `color-scheme` property, set to `dark` on `html.dark` in `src/app/globals.css` (GH #598). Without it the OS draws those controls light even in dark mode — e.g. a dropdown's option list renders white with light text. `dark:` classes only style the closed control, not the OS-drawn popup; `color-scheme` covers the rest.
- **Electron config**: electron-store for desktop persistence (connection mode, AI keys, currency, `exposeToLan`); localStorage fallback in web mode
- **IPC pattern**: `ipcMain.handle()` in `electron/main.ts`, exposed via `contextBridge` in `electron/preload.ts`, typed in `src/types/electron.d.ts`
- **Share on local network (v1.45)**: a Settings toggle backed by the electron-store key `exposeToLan` (default `false`). When off, the embedded Next server binds `localhost` (loopback-only, prior behaviour). When on, `electron/main.ts` respawns the server with `HOSTNAME=0.0.0.0` so other devices on the LAN (the mobile scanner) can reach it; the `get-lan-ip` IPC handler surfaces the reachable URL for the user. Flipping the toggle records `exposeToLanChanged` and respawns the server so the bind switches without an app restart. Pairs with mDNS for discovery. **The optional `FILAMENTDB_API_KEY` bearer gate is NOT a usable mitigation for the packaged desktop app (#828):** the decision lives in `src/lib/apiAuth.ts` (`decideApiAuth`, pure + unit-tested) and is enforced from `src/proxy.ts` — the Next 16 Proxy (formerly Middleware), whose `config.matcher` is `/api/:path*`, so it runs on EVERY API request including the first-party browser UI's same-origin fetches. It's an all-or-nothing gate with no same-origin exemption (deliberately — `Sec-Fetch`/`Origin` are spoofable by non-browser clients, #767), so setting it locks the desktop's own first-party web UI out of `/api` too. It's meant for headless / Docker deployments the mobile app or curl talk to, and there is no in-app setter (the server reads it only from its OS environment). The LAN-share Settings card discloses this posture with "there is no password".
- **mDNS auto-discovery (v1.47)**: `electron/mdns-service.ts` advertises the desktop as `_filamentdb._tcp` via `bonjour-service` (pure JS, no native dep) so the mobile app finds it without typing an IP. Advertised ONLY while `exposeToLan` is on — `syncMdnsAdvertisement()` in `electron/main.ts` starts/stops it on toggle and re-publishes after a server restart/health recovery. The mDNS instance name is suffixed with the hostname (`Filament DB (host)`) because bare-name collisions across two desktops would suppress the second on probe (#723).
- **OpenPrintTag**: CBOR encoder in `src/lib/openprinttag.ts`, NDEF wrapping in `src/lib/ndef.ts` (re-exported by `electron/ndef.ts`). CBOR aux_region_offset must point to valid CBOR within the NDEF payload (Prusa app requirement)
- **Bambu NFC**: MIFARE Classic decoder in `src/lib/bambuTag.ts` (re-exported by `electron/bambu-tag.ts`). HKDF-SHA256 key derivation from UID, binary block parser, maps to `DecodedOpenPrintTag`. Read-only (RSA-2048 signed tags)

## Internationalization (i18n)

- **Framework**: Custom React Context-based i18n (no external library), following the useCurrency pattern
- **Provider**: `src/i18n/TranslationProvider.tsx` — provides `t(key, params?)`, `locale`, `setLocale`
- **Locales**: `src/i18n/locales/en.json` (English), `src/i18n/locales/de.json` (German) — ~1490 flat key-value pairs (count drifts on every PR — `jq 'keys|length' src/i18n/locales/en.json` for current). Since v1.34.1 the `tests/i18n-key-coverage.test.ts` invariant enforces (a) every literal `t("…")` in `src/` resolves in both locales and (b) en+de carry the same key set — a new translation key MUST land in both files in the same PR.
- **Interpolation**: `{paramName}` tokens in translation strings, e.g. `t("sync.time.minutesAgo", { count: 5 })`. The substitution lives in `src/i18n/interpolate.ts` and answers **two** independent hazards — neither may be "simplified" away:
  1. **Function replacement, never a string** (v1.67, GH #1007 F1 / PR #1013) — a string second arg to `String.replace` corrupts param values containing `$$`/`$&`/`` $` ``/`$'` (e.g. a filament named "Cheap $$ PLA").
  2. **Single-pass scan, never a fold over `Object.entries(params)`** (GH #1029) — the old per-param loop re-scanned the OUTPUT of each pass, so a `{token}` inside an already-substituted VALUE was picked up as a live token by a later param and replaced (`{name: "PLA {count}", count: 7}` rendered "PLA 7"). Whether it bit depended on the CALL SITE's key insertion order, which is why it stayed latent. One `TOKEN_RE = /\{(\w+)\}/g` pass over the template makes an inserted value structurally unreachable as a token and removes the order dependence; it also stops splicing the param name into a `RegExp` unescaped (a key with regex metacharacters used to mis-match). The `\w+` class is pinned by a locale-token invariant test in `tests/i18nInterpolate.test.ts` — if a future dotted/hyphenated key trips it, widen the class rather than deleting the test.
- **Fallback chain**: current locale → English → raw key
- **Persistence**: electron-store (desktop) or localStorage (web), key `filamentdb-locale`
- **Settings**: Language selector in Settings → UI (`src/app/settings/ui/page.tsx`, same toggle-button pattern as Currency). Since #801 `src/app/settings/page.tsx` is a tile launcher only; every real panel lives in a sub-page under `src/app/settings/{ui,network,ai,backup,danger,devices}/`, and all five UI preferences (Currency, Theme, Date format, Number format, Language) are on the one UI page.
- **Adding a language**: Create `src/i18n/locales/xx.json` with all keys, add entry to `LOCALES` array in `src/i18n/index.ts`

## Testing

- ~3000 tests across ~145 files (unit + Mongoose model + Next.js route handlers). Exact counts drift on every PR — run `npm test` for the current numbers.
- **Test discovery is scoped to `tests/`** (`test.include: ["tests/**/*.test.ts"]` in `vitest.config.ts`) so a nested git worktree under `.claude/worktrees/` — or any other in-tree checkout — can't get its stale test copies swept into the run. Root ESLint likewise ignores `.claude/**` (`eslint.config.mjs`, #992) so a nested worktree can't fail lint either.
- Coverage thresholds: 99% lines, 98% statements, 96% functions, 96% branches (raised from 80/80/90/75 in the v1.62 coverage sweep (#942), which drove `src/lib/**` + `src/models/**` to ~99% lines / ~98% branches). Enforced on `src/lib/**` and `src/models/**`; `src/lib/compressImage.ts` and `src/lib/labelBitmap.ts` are excluded because their main flow is DOM/canvas-only — GH #526. The residual uncovered branches are provably-unreachable defensive guards (Mongoose always materialises array schema fields as `[]` + rejects invalid Dates at cast; WHATWG URL mandates a host for http(s); regexes capturing only finite numerics; internal-consistency asserts) — thresholds sit just below the achieved numbers so a real regression trips CI while normal churn doesn't.
- **Full DB-backed suite under `--coverage` needs capped parallelism.** v8 instrumentation + ~15 concurrent `mongodb-memory-server` instances (one `mongod` per test file via `tests/setup.ts` `beforeAll`) overwhelms the machine → `MongoNetworkTimeoutError` / hook timeouts. Run coverage with `--maxWorkers=4` (or fewer); the plain `npm test` run without instrumentation is fine at full parallelism.
- Setup file: `tests/setup.ts` (mongodb-memory-server). **Caveat**: setup wipes `mongoose.models` between tests; route-level tests that use `.populate(...)` must re-register models in `beforeEach` by calling `mongoose.model(name, schema)` directly (see `tests/locations-route.test.ts` for the pattern).
- Tests run in CI on Node 20 and 22

## CI/CD

- **The release/Docker publish paths run the FULL CI gate via a reusable workflow (`ci-gate.yml`, #852)**: lint, root `tsc --noEmit`, Electron typecheck (`electron:typecheck`), coverage-enforced tests (`test:coverage`), the `Security audit` step (`node scripts/audit-gate.mjs` — see below), `npm run build`, and the standalone production smoke test — plus, on `v*` tag runs only, a **`tag-version` job (#1037)** that fails the gate when the pushed tag doesn't match `package.json`'s version (a stale-version tag used to build fully GREEN while every update feed advertised the old version — silent, total auto-update failure; nearly shipped on v1.68.1). The job is skipped on branch/PR/branch-ref-dispatch runs (a TAG-ref dispatch of docker.yml re-runs it, intentionally) and is deliberately NOT mirrored into `test.yml` (never runs on a tag). `on: workflow_call`, invoked via `uses: ./.github/workflows/ci-gate.yml` by `release.yml` (a `gate` job that runs ONCE before the platform matrix; build legs `needs: gate`) and `docker.yml` (`needs: gate` before build+push). Before #852 those tag-triggered workflows re-implemented only a partial gate (lint + `npm test`), so a `v*` tag could publish from a commit branch-CI would reject (e.g. an Electron type error, since `electron/` is excluded from the root tsconfig). **Reusable-workflow refs resolve at the tagged commit**, so the tag must contain `ci-gate.yml` (true for any tag cut after #852). **`test.yml` deliberately stays INLINE** (not a caller of `ci-gate.yml`) — a reusable call would rename its checks to `gate / test (20)` etc. and break `main`'s branch protection (required contexts `test (20)`/`test (22)`/`smoke`). So `test.yml` and `ci-gate.yml` are TWO copies of the same gate that must be **kept in sync** (a cross-reference comment in each says so).
- **Security audit is a wrapper, not bare `npm audit` (#1025/#1023)**: both gate copies run `node scripts/audit-gate.mjs` (same command locally — there is no `npm run` alias). It shells `npm audit --json --audit-level=moderate` and fails on any advisory at moderate+ whose GHSA id isn't in the reviewed `.audit-allowlist.json`; allowlisted ones print as `ALLOWLISTED:` warnings. npm audit has no native exception mechanism, so one genuinely unfixable transitive advisory would otherwise red every run forever. Traps: each advisory is judged by its OWN `adv.severity` inside `via[]`, never the package's aggregate (the aggregate is the max, and `--audit-level` does NOT filter the JSON report); an exception binds to `(GHSA id, package)` — both must match; every entry MUST carry a `justification` (≥20 trimmed chars) and a parseable `reviewBy`, validated BEFORE any exception activates (a malformed entry fails the gate CLOSED, and an unparseable date would never compare as past so the expiry nudge would never fire); a past `reviewBy` warns and never fails, so a calendar can't break a release; and a broken audit service — which exits non-zero but emits a valid JSON error object with no `vulnerabilities` key — is rejected rather than read as "no advisories". **`packages/mobile` runs the SAME wrapper** via `mobile.yml` (`node scripts/audit-gate.mjs --dir packages/mobile --omit-dev`), against its OWN `packages/mobile/.audit-allowlist.json` — the audited tree and its allowlist always travel together, because that package vendors its own lockfile and its justifications describe its own exposure. `--dir` resolves against cwd and `--omit-dev` adds `--omit=dev`; no flags reproduces the historical root invocation exactly. Argument parsing (`parseAuditGateArgs`) throws on an unknown or value-less flag rather than ignoring it — a gate that audited the wrong tree because of a typo would exit 0 while proving nothing. Both committed allowlists are validated by `tests/auditGate.test.ts`, since the mobile gate is path-filtered and doesn't run on most PRs.
- **Tests**: `test.yml` runs the gate (test matrix Node 20+22 + smoke) inline on push to main and PRs.
- **Releases**: Triggered by `v*` tags (`release.yml`). Runs `ci-gate.yml` once, then builds macOS (x64+arm64), Windows (x64+arm64 — the arm64 installer is manual-download only; x64 is the sole Windows auto-update channel, #586), Linux (x64+arm64). Uploads assets to GitHub release.
- **Docker**: Triggered by `v*` tags (`docker.yml`, also `workflow_dispatch`). Runs `ci-gate.yml`, then builds the multi-arch (amd64+arm64) image (native per-arch runners → digest merge, #845) and pushes to GHCR.
- **Bundled technical-reference content is committed-snapshot-only (#853)**: `release.yml` NO LONGER runs `scripts/fetch-reference.mjs` per platform leg (it used to, best-effort, so legs could ship different `src/content/` content + `REFERENCE_WIKI_SHA` for the same tag). Every artifact (desktop + Docker) now ships the committed `src/content/referenceContent.ts` + `referenceIndex.ts`. **Refresh it via `npm run fetch:reference` in a PR before tagging**; the scheduled `reference-drift.yml` (weekly + `workflow_dispatch`) re-runs the generator against the live wiki and FAILS when the committed snapshot has drifted — a visible nudge, NOT a PR gate.
- **Version bump**: `release-bump.yml` (manual `workflow_dispatch` with a semver input) bumps the version across `package.json`, `package-lock.json`, and `public/openapi.json`, opens a bump PR, and enables auto-merge — so the version-bump commit goes through the same PR + CI gate as everything else (it needs a `RELEASE_BUMP_TOKEN` PAT secret). See "Release Process".
- **Mobile (EAS) build**: `eas-build-mobile.yml` (manual `workflow_dispatch`, platform + profile inputs) queues an Expo EAS Build of `packages/mobile` — the mobile app is managed Expo (CNG), so `ios/`/`android/` aren't committed and Xcode Cloud can't build it; EAS generates the native project + signs on Expo's servers. Needs an `EXPO_TOKEN` secret; `--no-wait` so it never blocks a runner. A repo-root `.easignore` scopes the upload to `packages/mobile`. See the "Mobile scanner app" section.
- **Mobile CI gate**: `mobile.yml` (#765) — a separate, path-filtered CI workflow that runs `packages/mobile`'s OWN lint + typecheck + audit (through the shared wrapper against the mobile allowlist — see the Security-audit bullet above) on push to main / PRs that touch `packages/mobile/**` (or the workflow file). Its job is NAMED `lint · typecheck · audit`, so a failure of any one step surfaces under all three names on the PR. It exists because the mobile package isn't an npm-workspace member and the root gate excludes `packages/` (root tsconfig/eslint/`npm ci` never touch it), so root CI can't catch mobile-only breakage or advisories. NOT a required branch-protection check (the paths filter would deadlock a required check), so it's a best-effort gate, not part of `ci-gate.yml`.
- **Lint rule**: `react-hooks/set-state-in-effect` — don't call setState directly in useEffect body; use lazy initializers or callbacks

## Release Process

1. Update version in **three** places (the release CI uses package-lock for `npm ci`, OpenAPI reports the API version in `/api-docs`):
   - `package.json` (top-level `version`)
   - `package-lock.json` (two occurrences: top-level `version` and `packages[""].version`)
   - `public/openapi.json` (`info.version`)
   - **Shortcut**: `gh workflow run release-bump.yml -f version=<x.y.z>` does all three + opens an auto-merging bump PR (avoids a direct push to protected `main`). Steps 2–3 below are the manual equivalent.
2. Commit and push to main with a `Bump version to <x.y.z>` message (or let the bump PR merge)
   - **Reference content (#853):** the bundled technical reference ships from the committed `src/content/` snapshot — it is NOT re-fetched at build time. If the wiki changed since the last refresh (the scheduled `reference-drift.yml` flags this), run `npm run fetch:reference` and land the regenerated `src/content/` in a PR BEFORE tagging, so the release ships current content.
3. After the bump lands on main, pull, tag with `git tag v<version>`, and push the tag (this triggers `ci-gate.yml` → the build matrix; a commit that fails the gate blocks the release instead of shipping, #852, and a tag that doesn't match `package.json`'s version fails the gate outright, #1037 — the bump-before-tag ordering is now machine-enforced)
4. CI builds desktop installers and uploads to a draft GitHub release. The release is auto-published when uploads finish; **assets ≠ source of truth for "release done"** — wait for the workflow run, not just the release-created event
5. Apply release notes with `gh release edit v<version> --notes-file …`. CI doesn't overwrite the body when it publishes, so a single edit (any time after the draft is created) suffices

### Release-process gotchas
- **CSP fixes affect TWO files.** The web CSP lives in `next.config.ts`; the Electron renderer applies its OWN CSP from `electron/main.ts`'s `onHeadersReceived` handler and the renderer doesn't merge them — the value set in Electron REPLACES whatever Next sent. Any `script-src` / `frame-src` / new-directive change has to land in both. Past regressions: v1.25.0 shipped with the web CSP gated for dev `'unsafe-eval'` but the Electron CSP unchanged (v1.25.1 patch); v1.30.3 fixed an `img-src 'https:'` asymmetry from #371. The one intentional asymmetry is `connect-src`: Electron adds `ws://localhost:* http://localhost:*` for the embedded Next server; everything else must stay in lockstep. `tests/csp-parity.test.ts` (GH #408) fails fast on drift — both directives are diffed at test time so a future asymmetry trips CI before it ships.
- **Dev vs packaged in Electron is `app.isPackaged`, not `NODE_ENV`.** `NODE_ENV` isn't reliably set when Electron launches the main process; gate Electron-specific dev-only behaviour on `app.isPackaged ? prod : dev`.
- **Historical (pre-#852): the Windows ARM64 release job ran the full Vitest suite under x64 emulation, making `mongodb-memory-server`'s then-10s startup timeout flaky** (`tests/compressImage.test.ts` was a victim on v1.25.0). Since #852 no release build leg runs tests at all — the gate runs once on ubuntu-latest (`ci-gate.yml`), so this failure mode can't recur on the cross runner. The launch timeout is 60s anyway (`MONGO_INSTANCE_LAUNCH_TIMEOUT_MS` in `tests/setup.ts`, bumped in v1.28).
- **macOS installs from an older app cache the bundle ID, not the binary.** A `.dmg` in Downloads doesn't replace `/Applications/Filament DB.app` until you drag it over. Verify with `defaults read /Applications/Filament\ DB.app/Contents/Info.plist CFBundleShortVersionString`.
- **Windows auto-update channel is x64-only, by design (GH #586).** The Windows updater metadata file is `latest.yml` with NO arch suffix (unlike `latest-mac.yml` / `latest-linux-arm64.yml`). The x64 and arm64 Windows release jobs each emit one, so before #586 the later upload won — and an x64 user served the arm64 `latest.yml` auto-installed an arm64 build that can't run on x64, producing Windows' "Problem with Shortcut — 'Filament DB.exe' has been changed or moved" error intermittently (every other release, by CI upload-order luck). The fix: the `win-arm64-cross` job runs electron-builder with `--publish never` AND deletes `dist-electron/latest.yml` before the softprops upload, so **x64 is the single Windows update channel**. x64 installers run on arm64 Windows via the OS emulation layer, so arm64 users still auto-update (to the emulated x64 build); the native arm64 installer stays on the release for manual download. If native-arm64 auto-update is ever wanted, the proper fix is a post-build job that merges the two jobs' `latest.yml` into one multi-arch file — which is exactly what the mac side now does. **macOS auto-update is correct-arch as of #698 (v1.40.1).** The mac jobs had the same latent `latest-mac.yml` collision, now resolved: macOS builds are Developer ID-signed + notarized (v1.39.1), `mac.target` is `[dmg, zip]` (electron-updater can't auto-update from a dmg — it throws "ZIP file not provided"), and the `merge-mac-metadata` job combines both arches' single-arch `latest-mac.yml` into ONE multi-arch file. electron-updater's `MacUpdater` filters that file's `files` by the running arch (keeps `arm64`-in-name files on Apple Silicon/Rosetta, the rest on Intel), so arm64 Macs auto-update to arm64 and Intel to x64. Both mac builds pass `--publish never` (like `win-arm64-cross`) so `merge-mac-metadata` is the SOLE writer of `latest-mac.yml`. If that job is skipped/fails after the installers upload, the release ends up with NO `latest-mac.yml` — safer than a *wrong-arch* one, but NOT harmless: the packaged app still runs `checkForUpdates()`, which 404s on the missing metadata and emits `state: "error"` in `electron/auto-updater.ts` → the amber error banner. macOS auto-update is then broken (and noisy) until corrected. A *single-arch* `latest-mac.yml` essentially can't ship: `scripts/merge-mac-latest-yml.mjs` throws if either arch's entry is missing (unit-tested in `tests/mergeMacLatestYml.test.ts`). **The silent-skip residual is closed as of #1037**: `merge-mac-metadata` carries `if: ${{ !cancelled() && needs.build.result != 'skipped' }}` (the second clause keeps it quiet when the GATE fails and build never ran — no artifacts to merge), so a failed NON-mac leg no longer skips it (both mac ymls exist → the mac channel ships intact), and a failed MAC leg turns the merge job loudly RED instead of silently skipping. The merge job also downloads every zip the merged feed references and verifies its **sha512 against the feed** before uploading it (a mac leg failing at its final installer-upload step, after its yml artifact was stashed, used to be the one path to a green merge over missing zips; and on a re-run over a stale same-named asset, a name-presence check would pass while electron-updater rejects the download on checksum — Codex P2 on PR #1058) — so a green `merge-mac-metadata` certifies the whole mac update channel, presence AND content. The post-release `gh release download v<ver> -p latest-mac.yml` check drops to belt-and-braces. Note the tag-version guard also runs on docker.yml's tag-ref `workflow_dispatch` re-publish path (#845) — a mismatched historical tag can't be silently re-published either. The `UpdateBanner` no longer gates the Download button off on macOS.

## PrusaSlicer Integration

- **Config bundle API**: `GET /api/filaments/prusaslicer` exports filaments as PrusaSlicer INI bundle; `POST` imports bundles back
- **Calibration API**: `GET /api/filaments/{id}/calibration?nozzle_diameter=0.4&high_flow=0|1` returns per-nozzle calibration data (extrusion multiplier, pressure advance, max volumetric speed, retraction); used by PrusaSlicer to auto-adjust filament settings when the user switches printer presets. Optional `high_flow` param disambiguates standard vs high-flow nozzles at the same diameter.
- **Spool check API**: `GET /api/filaments/{id}/spool-check?weight=42.5` checks whether any spool has enough remaining filament (by weight in grams) for a print job. PrusaSlicer calls this after slicing to warn if insufficient filament.
- **Sync with calibration context**: `POST /api/filaments/{id}?nozzle_diameter=0.4&high_flow=0|1` accepts optional query params so PrusaSlicer can write calibration-related keys (EM, PA, retraction) to the correct per-nozzle calibration entry
- **Match by stable id, not just name (#867, Phase 1)**: the sync historically keyed on the preset NAME, so a renamed preset stopped matching its filament and the fork's create-on-404 path silently spawned an orphan record that swallowed every later edit (a real "nothing syncs" footgun). The export (`filamentToSlicerKeys`) now round-trips `filamentdb_id` (the filament `_id`); the sync route (`POST /api/filaments/[id]`) resolves the target by **addressing mode** (Codex-hardened over 5 review rounds):
  - **ObjectId URL** (`POST /api/filaments/{ObjectId}`) is **authoritative** — resolve by that `_id`; a carried `filamentdb_id` must NOT override it (a copied/stale id in the config would otherwise redirect the write to the wrong row). A *found* ObjectId wins outright; if the 24-hex URL matches no `_id` (a preset legitimately NAMED with 24 hex chars), fall through to the name path below rather than 404. **Phase 2 companion (hyiger/PrusaSlicer#38):** the ObjectId path ALSO applies the request body's `name` to the record (a rename) when it differs — this is what makes the fork's "Update anyway" reconcile *stick* (otherwise the record keeps its old name and every later name-addressed sync re-hits `name_id_mismatch`). A rename colliding with another active filament returns **409 `name_taken`** (`conflictId` names it). The rename is SKIPPED when the request carries a `filamentdb_nozzle` hint (a per-nozzle preset's suffixed name is not a rename — see the per-nozzle bullet below). The name-addressed path NEVER renames (the name is its addressing key; a `body.name` there is ignored).
  - **NAME URL** (the fork's normal sync): resolve **filamentdb_id → name**, falling back gracefully when the id is absent/stale (it's DB-instance-specific).
  - **Name/id mismatch ⇒ 409, no mutation**: when a name-addressed sync's `filamentdb_id` resolves to a filament whose stored name differs from the preset name, the case is ambiguous — a *renamed preset* (id right) vs a *copied/cloned id* (id points at the wrong filament, e.g. a Save-As that kept the source's id), indistinguishable server-side. So the route **does not apply the update** (a copied id would silently overwrite the source); it returns **409 `name_id_mismatch`** with `{filamentId, matchedName, sentName}` so the fork prompts. To update the resolved filament anyway, re-sync by its ObjectId URL (the authoritative form). This also prevents the orphan (no 404 → no create-on-404). A recognized **per-nozzle preset** is exempt (`filamentdb_nozzle` hint present + the preset name decodes as `"<stored name> <hint>"`) — its name difference is the expected nozzle suffix, not ambiguity.
  - `filamentdb_id` is in `STRUCTURED_KEYS` so it's consumed for routing only, never stored in the settings bag. The **200** response (always = applied) carries `matchedBy` (`"id"|"name"|null`) + `matchedName` so the fork can re-stamp the id into a name-matched preset.
  - **Fork side (the `filamentdb_id` config option + send/clear-on-clone + the 409 reconcile prompt) is hyiger/PrusaSlicer#36; PrusaSlicer drops unknown config keys on load, so the key only persists with the FilamentDB fork.**
- **Per-nozzle preset fan-out (#872, refined in #950/#968/#969)**: a filament with calibrations on **≥2 distinct nozzles** (diameter + case-folded type + high-flow) exports as one FLAT preset per nozzle — PrusaSlicer has no parent/child for user filament presets — named `"<name> <nozzleSuffix>"` (`nozzleSuffix` = `"<diameter> <type>[ HF]"`, e.g. `"PLA 0.4 Brass HF"`), each baking its nozzle's filament-scoped calibration (pressure_advance is deliberately NOT baked — it stays dynamic via the /calibration endpoint); all siblings share ONE `filamentdb_id` and carry a `filamentdb_nozzle` routing hint (`generatePrusaSlicerBundle` in `src/lib/prusaSlicerBundle.ts`). **This is the ONLY path that still bakes a `compatible_printers_condition`** (ordinary exports derive nothing — see the next bullet and the v1.68.0 section), and there the restriction is the point: each section is tuned for exactly one nozzle. **High-flow disambiguation (#1040 / PR #1045, v1.70)**: `perNozzleCondition(nz, includeHfTerm)` emits `nozzle_diameter[0]==<Ø>`, plus ` and nozzle_high_flow[0]` / ` and ! nozzle_high_flow[0]` — note the **spaced `! `**, matching Prusa's own MK4S system profiles; an unspaced `!nozzle_high_flow[0]` reads as hand-typed user input and is never matched by the machine-shape predicates. The HF term is emitted ONLY when ambiguous: `generatePrusaSlicerBundle` builds a `hfStatesByDiameter` map over the fan-out group and passes `includeHfTerm` only where that diameter appears in BOTH highFlow states — always-emit would newly hide a 0.4-standard preset from a 0.4-HF printer, which is exactly the #1021 bug from the other direction. A slicer without the option fails open (visible everywhere = today's behaviour). Two predicates share one shape definition: `isMachineDerivedPerNozzleCondition(value, diameter)` (one known diameter, optional HF tail) for the fork sync-back strip, and `isAnyMachineDerivedNozzleCondition(value)` (diameter-agnostic, every vintage) for the bulk-import collapse AND the export-time bake gate — which fires when the bag value is absent, `""`, **or** machine-shaped, deliberately superseding #1021's "post-cleanup = user pin by construction" contract ON THE BAKE PATH (a tick-less sync leak can re-pollute the shared bag after the one-shot cleanup, which would leave the HF fix inert). **Trap (PR #1045 round 2): both predicates anchor to extruder index `[0]` only** — every exporter vintage only ever wrote index 0, and a `\d+` index classified a user's multi-extruder `nozzle_diameter[1]==0.4` pin as machine-derived and overwrote it. Bulk import collapses suffixed sections back to their base filament via `collapsePerNozzleImportSections` (drops the nozzle-baked keys + routing hints, omits temps/max-vol so an update can't clobber the base's shared values) so a round-trip doesn't spawn suffixed orphans. The sync route recognizes a per-nozzle preset (hint present + name decodes as `"<filament.name> <hint>"`, or ObjectId-addressed) and routes calibration keys to the hinted nozzle's calibration entry; recognized per-nozzle presets are **exempt from both the `name_id_mismatch` 409 and the ObjectId-path rename** (see the addressing bullets above). `filamentdb_nozzle` is consumed-never-stored alongside `filamentdb_id` in `STRUCTURED_KEYS`.
- **Field mapping**: `src/lib/prusaSlicerBundle.ts` maps structured DB fields → PrusaSlicer INI keys, merges with `settings` bag
- **Nil handling**: Structured DB fields that are null must NOT emit `nil` in the INI output — PrusaSlicer interprets nil as "reset to zero" for numeric fields. Only settings bag nil values (meaning "inherit from parent") are preserved. **Import side (v1.67, GH #1008 F3 / PR #1017): leave-when-omitted** — a name-matched bulk INI import used to null all four stored temps (and `inherits`) when the preset omitted those keys; the collapse now deletes each temp subfield the section didn't supply and drops an absent `inherits`, so omitted keys leave the stored values untouched while an EXPLICIT `nil` still writes null through (`src/lib/prusaSlicerBundle.ts`).
- **compatible_printers default**: `filamentToSlicerKeys` emits `compatible_printers = ` and `compatible_printers_condition = ` (both empty) by default, which PrusaSlicer treats as "no restriction" — synced filaments show up in every printer's dropdown and the scan-stream auto-select works regardless of active printer. Without this default PrusaSlicer treats the filaments as "compatible with no printer" and filters them out of every active printer's filament list. Gated on the key not already being present in the settings bag (`if (!("compatible_printers_condition" in keys))`), so a user-set restriction from a round-trip import survives the next export (PR #235) and PrusaSlicer's `nil` inheritance marker (a null bag value) still writes through as `nil`. **No condition is ever DERIVED from `compatibleNozzles` any more (#1021, v1.68.0)** — that derivation made PrusaSlicer silently hide presets; the ticks are bookkeeping + calibration scaffolding again. See the v1.68.0 section for the one-shot DB cleanup of already-persisted machine values and the permanent ingestion strip. **The preserved pin is now VISIBLE and EDITABLE (#1066)**: a preset duplicated in the slicer from another printer's profile carries its source's `compatible_printers_condition` (e.g. `printer_model=~/(COREONE|…)/`) into the bag, which hid the synced preset on every other printer with no in-app cause or remedy. The FilamentForm Slicer tab surfaces `compatible_printers` + `compatible_printers_condition` as editable fields (written to the bag only when EDITED, so a stored `nil` marker survives unrelated saves; cleared → explicit `""` = no restriction), and the detail page's Export-for-slicer disclosure shows an amber notice when the bag pins a restriction. Same PR: the per-id sync **lifts `inherits` to the top-level field** (it's in `INI_TOP_LEVEL_SETTING_KEYS`, but the sync used to bag it verbatim — the fork's whole-preset echo re-created a bag shadow that the export's settings seed kept emitting even after the form cleared the top-level value); the stored shadow is purged on sync (adopting its value top-level first when the **effective, parent-resolved** value was empty — a parent-supplied `inherits` masked the shadow in every export, so adopting there would pin it as a variant override) and the form kills it on every save (the form seeds its Inherits field through the same adopt gate). The lifted value keeps the GH #266 bounded-write cap (400 over `MAX_SETTING_VALUE_LENGTH`). LWW caveat: clearing the pin in-app doesn't update a still-restricted preset inside a RUNNING PrusaSlicer — its next sync re-pins until the slicer-side preset is refreshed (restart/re-import).
- **PrusaSlicer Filament Edition**: [hyiger/PrusaSlicer](https://github.com/hyiger/PrusaSlicer) has a `FilamentDB` module that fetches presets on startup via the REST API, syncs changes back with per-nozzle calibration context
- **NFC scan → preset select (SSE)**: `GET /api/scan/stream` is a long-lived Server-Sent Events endpoint that emits each NFC tag read (after the renderer matches it against the DB) as a `scan` event. Event payload: `{ timestamp, filament, candidates, decoded }` — `filament` is the matched DB row or null; PrusaSlicer keys presets by name so the consumer reads `filament.name` and calls its own "select filament for current extruder" path. The renderer pushes via `POST /api/scan/publish`; the in-process bus lives in `src/lib/scanBus.ts` (Node EventEmitter on `globalThis`). On connect the most recent scan is replayed once as a `replay` event so a slicer opened just after a tag read still picks it up; suppress with `?replay=0`. Heartbeats (`: hb`) every 25s keep proxies from idling the connection out. **In-process means one Filament DB instance, not one physical machine** — subscribers can be anywhere reachable over HTTP (a Pi running Filament DB can drive PrusaSlicer on a Mac across the LAN). What pins to a single machine is the publisher: NFC reads are emitted from the Electron renderer's `NfcProvider`, so the reader must be plugged into whichever box runs the Electron app. A headless Docker / web-only deploy has no `NfcProvider` and never publishes. A horizontally-scaled multi-process deployment would need an external broker behind the bus.
- **Port**: Dev and desktop use port **3456** (`next dev -p 3456`, Electron startup). Docker exposes the app on container port **3000** and is normally mapped with `-p 3456:3000`. PrusaSlicer defaults to `http://localhost:3456`.

## OpenTag3D read support (#864)

Read-only support for **OpenTag3D** tags (Polar Filament, American Filament, Numakers, 3D-Fuel, Ecogenesis), alongside the existing OpenPrintTag + Bambu readers — Filament DB as a neutral multi-standard reader. **Encoding settled empirically:** OpenTag3D v1.000 is a **FIXED BINARY MEMORY MAP** (absolute byte offsets, big-endian ints, UTF-8 strings, RGBA quads) — NOT CBOR. The "is it CBOR?" confusion came from conflating it with **OpenPrintTag** (Prusa, CBOR, MIME `application/vnd.openprinttag`), a *different* standard. OpenTag3D uses MIME `application/opentag3d`, and **both records can coexist on one physical tag**, so codec dispatch is per-NDEF-record-MIME, NOT per-chip.

- **Codec (`src/lib/opentag3d.ts`, DB-free)**: single source-of-truth field table transcribed from the authoritative `https://opentag3d.info/spec.json` (Core `0x00–0x65` with reserved gaps `0x0C–0x1A` + `0x4F`; Extended `0x70–0xBA`). Decoding rule: `real = raw * scaling`. `encodeOpenTag3D`/`decodeOpenTag3D` are symmetric over the table (round-trip tested). Tag-version policy: refuse a newer MAJOR, warn-but-parse a newer MINOR. `src/lib/opentag3d-decode.ts` maps decoded fields onto the shared `DecodedOpenPrintTag` shape (`tagSource: "opentag3d"`); OpenTag3D-only fields with no first-class home (MFI block, spool-core diameter, `td` mm, the vso triple, serial, online URL) ride `aux.opentag3d_*` so nothing is lost. **Unit traps:** `dry_time` is HOURS (converted ×60 to the minutes `dryingTime` expects); `td` is mm and is intentionally NOT mapped onto `transmissionDistance` (OpenPrintTag's HueForge TD — different quantity).
- **Pluggable codec registry (`src/lib/tagCodecs.ts`)**: `selectCodec`/`decodeFromNdefRecords` pick the first registered codec whose `ndefMime` matches a present TNF=0x02 record (OpenPrintTag preferred when both coexist). Shared by the desktop reader AND the server route — one decoder, no drift. Bambu MIFARE stays a separate non-NDEF path but emits the same decoded shape.
- **NDEF generalization (`src/lib/ndef.ts`)**: `parseNdefRecords(raw, ccOffset)` returns ALL records (`{tnf,type,payload}`); `ccOffset=0` for Type-5 (SLIX2), `12` for Type-2 (NTAG, CC at page 3 / byte 12, TLV at byte 16). `parseNdefFromTag` is now a back-compat wrapper (OPT payload only). `parseNdefRecordsAuto` tries `0` then `12`. Type-2 build helpers (`buildMediaNdefRecord`/`buildNdefMessageTlv`/`buildType2Cc`) feed the dev write CLI.
- **Desktop NTAG transport (`electron/nfc-service.ts`)**: `readNtagTag` reads NTAG via the `FF B0` READ BINARY pseudo-APDU (same style as the Bambu MIFARE path; no auth, no `FF FB` pass-through), validates the Type-2 CC, assembles the image, decodes via the registry. `readTag()` order: Bambu (MIFARE auth) → NTAG (`FF B0`; null = "not Type-2" → fall through, throw = real Type-2 content error → surface) → ISO-15693 (SLIX2; now registry-routed so an `application/opentag3d` record on SLIX2 decodes too). The read EXTENT is bounded by the pure `src/lib/ntagPages.ts` (#1028 — see the v1.68.1 section); one authoritative hardware-status statement lives in the "Hardware status" bullet below.
- **Server auto-sniff (`/api/nfc/decode`)**: accepts `tagType: "opentag3d"`; a raw `tagMemory` dump is auto-sniffed (CC-offset + MIME) via the registry regardless of the `tagType` hint, so the mobile client needs no format-detection. `payload`-only (pre-parsed) uses `tagType` to pick the codec.
- **Create-from-tag uses the recommended temp, not the range max (v1.67, GH #1008 F6 / PR #1017)**: `decodedTagToFilamentPayload` (`src/lib/decodedTagToFilament.ts`) prefers `aux.opentag3d_recommended_print_temp_c` / `_bed_temp_c` (finite-number-coerced) for the everyday `temperatures.nozzle`/`bed`; the tag's range max still lands in `nozzleRangeMax` (`decoded.nozzleTemp`).
- **Dev write harness (`scripts/write-opentag3d-tag.ts`, `npm run nfc:write-opentag3d`)**: flashes a blank NTAG via `FF D6` UPDATE BINARY. Predates the product write path below; still handy for generating a test tag from CLI flags without a commercial spool, and the encoder doubles as the test-fixture source.
- **Product write/erase/read-only (tag-type-aware)**: the detail-page **Write NFC** button and **Settings → Devices → NFC Tools** (Erase, Set read-only / Make writable) auto-detect the loaded chip and act on the right standard — **SLIX2 → OpenPrintTag** (ISO-15693 `FF FB`), **NTAG213/215/216 → OpenTag3D** (`FF B0`/`FF D6` Type-2). `NfcService.detectTag()` (IPC `nfc-detect-tag`) reports `{family, standard, formatted, readOnly}`; the renderer picks the encoder (`filamentToOpenTag3DFields`→`encodeOpenTag3D` for NTAG via `src/lib/opentag3d-encode.ts`, vs `generateOpenPrintTagBinary` for SLIX2) and sends a `standard` discriminator on `nfc-write-tag`; the service routes the transport and refuses a chip/standard mismatch (`TAG_TYPE_MISMATCH`). The SLIX2 path is unchanged (extracted to `writeSlix2Impl`/`formatTagImpl`/`setReadOnlyImpl`); the NTAG path adds `writeNtagImpl`/`formatNtagImpl` + `writeNtagPage` (there is no NTAG set-read-only impl — `setReadOnlyImpl` throws `NTAG_READONLY_UNSUPPORTED` for NTAG, per the next bullet).
  - **NTAG read-only is NOT supported** (read-only is a SLIX2/OpenPrintTag-only feature). Hardware testing showed the NTAG21x Capability Container (page 3) is **OTP** — a write that clears a CC bit returns SW 9000 but the bit persists (the read-only nibble goes `0x0→0xF` but never back). So a CC-nibble read-only is irreversible, and the static/dynamic lock bytes are likewise OTP/bricking — there's no reversible NTAG read-only. `setReadOnly` for an NTAG throws `NTAG_READONLY_UNSUPPORTED`; the NFC Tools read-only buttons disable when an NTAG is loaded. The write path does NOT honor the CC read-only nibble either (it's unreliable + can't be undone — a genuinely lock-byte-locked tag instead fails the page write naturally). **Writes only ever touch page 3 (CC), page 4 (TLV start), and page 5→last-user-page (zero-fill) — the static lock bytes (page 2) and dynamic/config lock pages are NEVER written.**
  - **Blank-NTAG sizing (#973)**: a blank tag has no CC to read its size from, so `getNtagNdefBytesViaGetVersion` issues `GET_VERSION` (`60h`) and maps the NXP storage-size byte (datasheet §8.3.7: `0x0F`=213/144B, `0x11`=215/496B, `0x13`=216/872B). Parsing is **offset-tolerant** — the pure `parseNtagNdefBytesFromGetVersion` (`src/lib/ntagVersion.ts`, unit-tested) SCANS the response for the NXP NTAG21x signature rather than hard-indexing byte 6 (#927 hard-indexed `data[6]`, never hardware-verified; on the ACR1552U a real 215 was mis-read as a 213). When GET_VERSION doesn't answer (no signature → null) the app no longer silently downgrades to a 144-byte NTAG213: the detail-page write **prompts the user to pick the NTAG type** (213/215/216) — the same posture as the dev CLI's `--ntag` — threaded through `nfcWriteTag(..., ntagSize)` → `writeNtagImpl`. Family confirmation then rests on the byte-0 NXP guard + CC 0xE1/0x00 guard + `writeNtagPage [3,255]` bound (the guards the proven dev CLI relies on; it never issued GET_VERSION). `getNtagNdefBytesViaGetVersion` logs the raw response + parsed capacity for on-device diagnosis. A formatted tag's existing CC is trusted (the common case).

A "Remember this — don't ask again" checkbox on the size picker saves the choice; a concrete size is then applied silently and only `"ask"` still prompts.
  - **Hardware status** (single source of truth for this section — per transport, not per feature):
    - **`FF B0` READ BINARY — PROVEN on the ACR1552U.** NTAG read (the read dialog + `aux.opentag3d_*`) works, and the same probe is what the write path uses as its brick guard.
    - **`FF D6` UPDATE BINARY page write — PROVEN on the ACR1552U + NTAG215** (`writeNtagPage`'s docblock: ported verbatim from the dev harness's `writePage`).
    - **`GET_VERSION` — CONFIRMED REJECTED on the ACR1552U, not "pending".** PR #979 (driven by an on-hardware log from #973) records SW `0x6900` "command not allowed": the reader refuses the command, so blank-NTAG auto-sizing can never work there. The fix was to stop depending on it — `resolveNtagWriteSize` (`src/lib/ntagVersion.ts`, pure + unit-tested) takes GET_VERSION when it answers, else the **user-declared** NTAG size (authoritative: it rewrites the CC, which self-corrects a tag an earlier bad write mis-sized), else refuses with `NTAG_SIZE_UNKNOWN`. `getNtagNdefBytesViaGetVersion`'s own docblock still says "HARDWARE-UNVERIFIED"; that phrasing predates the capture.
    - **Erase requires a PROVEN size (#978, round-8 fixed point).** GET_VERSION when it answers; on GET_VERSION-dead readers (ACR1552U) a single non-mutating probe of the NTAG216 physical tail (`NTAG_PHYSICAL_LAST_PAGE`) — a successful read is a proof auth protection cannot fake, so a full 216 erases hands-free. EVERYTHING ELSE refuses as `NTAG_SIZE_AMBIGUOUS`: any sub-216 conclusion requires a NAK, and a NAK is indistinguishable from a password-protected in-range page at the PC/SC layer. Four heuristic tie-breakers fell in the #1172 review (user pick → undersize hole; blanket NAK demotion → transport-blip undersize; user-extent probes → NTAG212 config tails read fine; CC cross-check → broken in BOTH directions by protected+mis-formatted combos) — only proofs remain. The pure `resolveNtagEraseSize` is `verSize ?? provenBytes ?? refuse`; transport blips retry ×3 then `NTAG_PROBE_FAILED`. Write NFC remains the universal workaround (explicit size + CC rewrite). On-device confirmation on the ACR1552U still owed.

- **Spool printer-slot assignment (#242)**: a spool can be assigned to a printer AMS/MMU slot directly from the spool card, distinct from its Location — Location is the spool's semi-permanent "home", the slot is its transient position while loaded in a printer. `src/lib/spoolSlots.ts` is the enforcement point: `findSpoolSlot` (reverse lookup over `Printer.amsSlots[].spoolId`), `assignSpoolToSlot` (clears the spool from every slot, then sets the target — a spool occupies at most one slot, and bad data with a spool in two slots self-heals), `clearSpoolsFromOtherPrinters` (post-save reconciliation wired into the printer PUT/POST so the one-slot invariant holds no matter which form wrote it). - **Resolver** (`src/lib/resolveFilament.ts`): `secondaryColors` is array-fallback inheritable like `optTags` / `bedTypeTemps` — a variant either declares its own non-empty array or inherits the parent's whole array. Setting a variant's array to `[]` does NOT clear; it falls through to the parent. To override and show as single-color, give it at least one secondary slot or a different arrangement.
- **Read path** (`/api/filaments` list aggregation + `/api/filaments/[id]` variants subquery + parent summary): `secondaryColors` rides the projection, with effective-array merge mirroring `optTags` — same `$ifNull` + parent-`$lookup` pattern. Dashboard + filament list both consume `displayColor()` for their one-color spots.
- **`<FilamentSwatch>`** (`src/components/FilamentSwatch.tsx`): extended with `secondaryColors?: string[]` + `arrangement?: ColorArrangement`. Coextruded renders as hard-stop stripes via `linear-gradient(to right, c0 0%, c0 N%, c1 N%, ...)`; gradient renders as smooth `linear-gradient`. The finish overlay (matte / silk / sparkle / glow / translucent / transparent) still composes on top. Single-color callers are unchanged (backward-compatible). `FilamentForm`'s `MultiColorEditor` sub-component drives an arrangement radio (sets `optTags` 28/29 for coextruded — dual vs triple by color count — or 27 for gradient), 0–5 secondary color slot editor, and a live preview swatch that passes `null` color when coextruded for WYSIWYG.
- **OpenPrintTag encode/decode** (`src/lib/openprinttag.ts` + `-decode.ts`): `OPT_KEY.SECONDARY_COLOR_0..4` (CBOR keys 20–24). Encoder loops `secondaryColors.slice(0, 5)` into the right slots, parses each as RGBA, emits CBOR bytes. Decoder reads slots in order and surfaces them as `decoded.secondaryColors`. **Documented spec gap**: the alpha byte from `color_rgba` is truncated (`bytesToRgbHex` returns `#rrggbb` not `#rrggbbaa`) — translucency is modelled via finish optTags with real CSS opacity, not the alpha byte, which would be redundant. Round-trip nfc test pins this.
- **OPT DB import** (`src/lib/openprinttagBrowser.ts` + `/api/openprinttag/import`): `OPTMaterial.secondaryColors` parsed from raw `secondary_color_0..4` YAML fields. When a material has secondaries, the importer preserves a null primary on update (`color: m.color || (m.secondaryColors.length > 0 ? null : "#808080")`) AND clears the gray sentinel `"#808080"` to null on conditional-update when adopting coextruded secondaries — so re-importing an OPT material that's coextruded doesn't leave a stale gray primary.
- **NFC scan → form prefill** (`src/components/NfcReadDialog.tsx` + `/filaments/new/page.tsx`): `secondaryColors` ride as a comma-separated URL param, validated entry-by-entry as `#RRGGBB`, threaded through `initialData`.
- **CSV import/export** (`src/lib/importFilaments.ts` + `exportFilaments.ts`): `Secondary Colors` column (comma-separated). Importer parses, trims, drops malformed, caps at 5. When `secondaryColors` has entries AND `row.color` is null/empty, the importer explicitly sets `doc.color = null` to preserve a null primary on coextruded CSV round-trip.
- **Slicer-bound export — drop secondaries, never invent gray** (`src/lib/prusaSlicerBundle.ts` + `orcaSlicerBundle.ts`): a local `slicerExportColor(filament)` helper falls through `color → secondaryColors[0] → null` (returns `null` rather than `displayColor()`'s `"#808080"` sentinel so `set()` is a no-op when neither exists — the slicer uses its own default rather than getting forced to a gray the user never picked, the Codex P2 fix on PR #485). Single-filament + bulk exports both pass through this helper. Notice surfaces on the "Export for slicer" disclosure when `secondaryColors[].length > 0` so the user sees the trade-off before download.
- **OpenAPI** (`public/openapi.json`): `Filament.color` marked `nullable: true` with a description naming the OPT spec gap (alpha byte not stored), `Filament.secondaryColors` defined as a max-5 array of `^#[0-9A-Fa-f]{6}$` strings, both notes call out the slicer-export drop.

## Color-name typeahead → hex

`FilamentForm`'s "Color Name" input is a combobox: typing populates a dropdown of suggestions, picking one sets BOTH the color name and the hex color picker. Two suggestion sources, in priority order:

- **From your filaments** — the user's previously-saved `(colorName, color)` pairs, served by a new `GET /api/filaments/colors` endpoint that runs `$group` over non-deleted filaments. Multiple filaments with the same name+hex collapse to one row; different hexes under the same name (e.g. three brands of "Galaxy Black" with slightly different shades) stay separate so the user can pick the right shade.
- **Standard colors** — the 148 CSS Color Module Level 4 named colors plus the gray/grey + cyan/aqua + fuchsia/magenta + slategray/slategrey synonyms. `src/lib/cssNamedColors.ts` is the source of truth.

Lookup helpers in `src/lib/cssNamedColors.ts`:
- `lookupCssNamedColor(name)` — case- and whitespace-insensitive. Returns the canonical uppercase hex (`#000080` for any of `navy`, `Navy`, `  NAVY  `) or `null`.
- `filterColorSuggestions(dbSuggestions, query, maxResults?)` — substring-matches the query against both sources, dedupes by `(lowercase name, uppercase hex)` (DB wins ties), and orders DB entries above CSS entries. Exported because the combobox can't unit-test through it.

Commit-on-write rules in the combobox. **All hex-writing commits are gated on the `colorHexUserSet` flag (#794, v1.55):** a name commit fills/replaces the hex ONLY when the hex isn't "user-owned" — i.e. it's blank/incomplete, never picked, or was itself auto-filled by a prior name commit. Once the user edits the hex via the color picker or hex text field it's owned, and from then on a name is just a *label* and never overwrites it.
- **Click / Enter on a dropdown row** sets `colorName`, and sets `color` only when the hex isn't user-owned.
- **Tab-out / blur with an exact CSS named-color match** updates the hex (even without opening the dropdown) only when the hex isn't user-owned — covers users who already know "navy" and just want to type it.
- **DB-side blur lookup is intentionally NOT auto-applied** — the same name can have multiple legitimate hexes in the DB; the user has to pick which one they meant via the dropdown.
- **Plain typing never overwrites the hex** — only an explicit, non-user-owned commit (click/Enter/exact-CSS-on-blur) changes the color picker, so the user's free-text "I'm naming this whatever I want" path stays uninterrupted.

Translation keys: `form.colorName.section.db` ("From your filaments" / "Aus deinen Filamenten") and `form.colorName.section.css` ("Standard colors" / "Standardfarben") in both `en.json` and `de.json`.

## Finish indicator on the swatch + name chip

When two filaments share the same color but a different finish (the canonical case: white plain / matte / silk), the inventory list, detail page header, and the color-variants list under a parent now distinguish them visually:

- **`<FilamentSwatch>` finish texture**: a new `finish?: "matte" | "silk" | "sparkle" | "glow" | "translucent" | "transparent" | null` prop drives a CSS overlay on top of the color. Matte = flat fill (no highlight), silk = soft sheen gradient, sparkle = four small dots whose color flips based on the underlying fill's luminance, glow = soft yellow inner halo, translucent/transparent = real alpha (55% / 25%) over a checkered backdrop (the universal "see-through" signal). All five non-alpha treatments compose with `data-finish="..."` for QA snapshots.
- **`<FinishChip>`** renders the same finish as a small uppercase chip beside the filament name. Per-finish color palette (silk = blue, sparkle = amber, glow = yellow, translucent = cyan, transparent = slate, matte = gray) and reuses the existing chip styling vocabulary.
- **Source of truth**: `src/lib/filamentFinish.ts`'s `deriveFinish(optTags)` maps optTag IDs to a single canonical finish string. Priority order when a filament carries multiple finish-relevant tags: `transparent > translucent > sparkle > silk > glow > matte`. Parents are finish-agnostic — finishes are only derived for variants and standalones; `<FilamentSwatch isParent>` short-circuits to the parent render (composite-of-variant-colors since GH #597, cross-hatch fallback) regardless of finish.
- **Data plumbing**: `optTags` rides the list aggregation (`GET /api/filaments`) and the per-parent variant projection in `GET /api/filaments/{id}` (`.select("name color cost optTags")`) so neither the list page nor the detail-page color-variants list need a follow-up fetch. `FilamentSummary` and `FilamentVariant` types gain `optTags?: number[]`.
- **Translations**: new keys `swatch.finish.matte`/`silk`/`sparkle`/`glow`/`translucent`/`transparent` in both `en.json` and `de.json`. Kept distinct from the existing `form.tag.*` keys so chip text can diverge from form-checkbox labels without coupling them.

## Multi-color parent indicator + Create-variant flow

*(This section covers the RENDERING of a parent. What a parent is allowed to HOLD — since v1.70 a parent is a template: colorless, no inventory — is the v1.70 section.)*

- **Multi-color parent swatch (auto-detected)**: a filament that currently has ≥1 non-deleted variant is treated as a "parent of color variants". **A filament is never a parent unless it actually has variants** — there is no schema flag; parenthood is derived from the variant count (`hasVariants` in `src/lib/resolveFilament.ts`: `countDocuments({ parentId, _deletedAt: null }) > 0`). Rendering is centralised in `src/components/FilamentSwatch.tsx` (`<FilamentSwatch color={...} isParent variantColors={...} />`), used by the inventory list (`src/app/page.tsx`), the detail page header (`src/app/filaments/[id]/page.tsx`), the variant chips in the parent's color-variants list, and the new-filament form's parent picker chip + dropdown rows (`src/app/filaments/FilamentForm.tsx`).
  - **Composite color swatch (GH #597)**: a parent swatch renders a composite of the group's actual colors via the pure `parentSwatchColors(colors)` helper in `src/lib/filamentColors.ts` — **one flat ordered candidate array, not `(parentColor, variantColors)`**; the caller owns the ordering (parent's own `color` + its `secondaryColors` first, then each variant's colors). Validates `#rgb`/`#rrggbb`, case-insensitive dedupe keeping the first occurrence's casing, everything else dropped. **Callers must pass every color SOURCE, not just each row's primary** (Codex P2 on PR #600): a coextruded/gradient member has `color: null` and its colors live entirely in `secondaryColors`, so a primaries-only list silently drops it from the composite — which is why both call sites pass `variants.flatMap((v) => [v.color, ...(v.secondaryColors ?? [])])`. One color → solid fill; ≥2 → equal-width hard-stop segments (same construction as the coextruded multi-color swatch). `FilamentSwatch` calls it TWICE, and the two-step is load-bearing: `parentSwatchColors(variantColors)` first, and the full `parentSwatchColors([color, ...secondaryColors, ...knownVariantColors])` composite only when the VARIANTS contributed ≥1 valid color — otherwise a parent's own color alone would render a plain solid swatch indistinguishable from a regular filament (Codex P2 #600 round 3). **Falls back to the legacy neutral cross-hatch only when no valid colors are known** (e.g. a parent + variants all without a color), or where `variantColors` isn't plumbed (the parent picker, which has no variant colors handy — still cross-hatches). Earlier behaviour was always-cross-hatch; #597 changed it because a reporter (correctly) found the opaque white hatch unintuitive when the group has real colors.
- **`hasVariants` boolean on the list APIs**: `GET /api/filaments` extends the existing aggregation with a second `$lookup` (probe-style — capped at 1 doc — joining `_id → parentId` on non-deleted rows) and exposes `hasVariants: boolean` next to the existing `hasCalibrations`. `GET /api/filaments/parents` does the equivalent with a single `Filament.distinct("parentId", ...)` call so each parent option in the picker can render the cross-hatched swatch when it has variants and a solid one when it doesn't.
- **"Create variant" CTA on the filament detail page**: a `bg-fuchsia-600` button next to the existing Clone, gated on `!isVariant`, links to `/filaments/new?parentId=<id>`. When it shipped this was a pure discoverability fix over the existing `?parentId=` flow — **no longer true since v1.70**: creating the FIRST variant of a parent that still carries a color or inventory is a gated two-step server contract (409 `parent_promotion_required` → replay with `promoteParent: true`), so the create path restructures a second document. See the v1.70 section. Translation keys: `detail.createVariant`, `detail.createVariant.title` (both `en.json` and `de.json`).
- **Parent values as placeholders in the new-filament form**: when `/filaments/new` is opened with `?parentId=`, the page now fetches the parent with `?raw=true` and passes the full doc on `initialData._parent`. `FilamentForm` exposes an inline `parentPh(path)` helper that returns the parent's stringified value (or `undefined`) and threads it into every inheritable scalar input's `placeholder` — cost, density, diameter, the seven `temperatures.*`, min/max print speed, drying temp/time, shore A/D, glass-temp, heat-deflection, transmission distance, shrinkage XY/Z, tdsUrl, etc. **Placeholders are display-only and must NOT be auto-copied into form state** — the submit handler at `src/app/filaments/FilamentForm.tsx` builds the body from `form.*` only, so a blank input stays blank on the variant doc and continues to track the parent dynamically via `resolveFilament()` at read time (GH #106). The existing variant-banner at the top of the form fires for both edit AND new flows now that `_parent` is populated either way.

## Trusted-origin (CSRF) guard sweep

`assertSameOriginRequest` (`src/lib/requestGuard.ts`) was originally added in GH #252 for snapshot export·restore·wipe + the MongoDB connection test + the Atlas import (the obviously destructive admin handlers). GH #360 extended it to every other mutating API route — POST/PUT/DELETE/PATCH on filaments, nozzles, printers, locations, bed-types, print-history, spools and assignments, share + share/[slug], scan/publish, prusament/import, openprinttag/import, tds, and all the import-* endpoints. Same pattern at the top of each handler:

```ts
const guard = assertSameOriginRequest(request);
if (guard) return guard;
```

The guard rejects browser cross-origin (`Sec-Fetch-Site: cross-site` / `same-site`, or an `Origin` whose authority doesn't match `Host`) with 403, and lets non-browser clients (curl, PrusaSlicer / OrcaSlicer integrations) pass — they send neither header. **One stub left unguarded on purpose**: `POST /api/filaments/orcaslicer` is a 501 placeholder for the not-yet-implemented bulk OrcaSlicer importer; no destructive op runs and the handler takes no `request` argument. When bulk import lands, add the guard then.

Regression coverage in `tests/destructive-route-guard.test.ts` pins a representative sample (filaments / nozzles / locations / share / scan-publish / spools-import / print-history) so a future contributor can't quietly drop the guard from a new route. The Codex audit issue #360 has the full inventory.

## Label printers — Brother PT-P710BT (spool labels) + KNAON Y813BT (dry-box labels)

Two independent label printers, deliberately NOT one surface with a "which printer?" toggle: they print different things on different stock in different wire formats. Each owns its emitter, its electron-store device key, its managed CUPS queue, its IPC channel trio and its Settings panel; they SHARE only the byte-agnostic OS print transport, the printer-listing IPC, and the public-URL setting. This section covers the Brother PT-P710BT raster path; the KNAON TSPL path is in the v1.69 section, and the parts that had to become printer-aware are called out below.

End-to-end USB label printing for the Brother PT-P710BT (P-touch CUBE) — Electron-only feature, shipped in v1.34.0 (PR #487), transport reworked from Bluetooth-serial to the OS print system in GH #588 (v1.34.x) after a hardware test found the original path couldn't reach the USB device. Architecture worth knowing about before touching the code:

- **Transport is the OS print system, not serialport (GH #588).** On the desktop the PT-P710BT's Bluetooth is iOS/Android only (Brother's official line); over USB it's a **USB printer-class** device, NOT a serial port — so `serialport` (the old transport) could only ever reach the unsupported, flaky Bluetooth-SPP node, never the USB device. The current transport hands the raster byte stream to the platform print stack, which owns the USB device + driver: **macOS/Linux → CUPS** (`lp -o raw`; for a raw `usb://…` device with no installed queue we auto-manage a hidden raw queue `FilamentDB_Label` bound to it via `lpadmin`); **Windows → the spooler** (`RAW` datatype via a PowerShell winspool `WritePrinter` P/Invoke). `serialport` and its native-binding loaders (`@serialport/*`, `node-gyp-build`, `node-addon-api`) were dropped entirely. macOS USB is hardware-validated; Windows + Linux are implemented but need on-hardware verification.
- **Encoder is pure JS, browser-safe** (`src/lib/labelEncoder.ts`). Implements Brother's [Raster Command Reference for PT-E550W/P750W/P710BT](https://download.brother.com/welcome/docp100064/cv_pte550wp750wp710bt_eng_raster_102.pdf). Shared by the renderer dialog, the standalone CLI (`scripts/print-label.ts`), and the simulator that decodes the byte stream back into a PNG (`scripts/print-label-sim.ts`). Tape width 24mm rounds to media-byte 24; 3.5mm rounds to 4 (Brother's wire convention — `Math.round` covers both).
- **Bitmap rendering** (`src/lib/labelBitmap.ts`) is browser-only — uses HTMLCanvasElement + the `qrcode` npm. Renders QR + filament name at the print head's native 128-dot density, rotates 90° for raster-line orientation, thresholds to 1-bit grayscale ready for `packGrayscaleBitmap()`. **Orientation fix (GH #587):** after the 90° rotation it **reverses the raster-line order** — feeding lines in the rotate-order printed the label MIRRORED along its length (text backwards, QR reversed), confirmed on a real PT-P710BT. The printer's physical feed direction is opposite the raster-line order; reversing it un-mirrors the label. The CLI (`scripts/print-label.ts`) carries the identical reversal. QR sizing picks the largest module scale that fits `PRINT_HEAD_DOTS - 2 * VERTICAL_PADDING_DOTS = 116` dots after including the spec-required 4-module quiet zone (rendered with `margin: 4`). Payloads too long to fit even at scale 1 throw — no silent clipping.
- **Transport** (`electron/label-printer.ts`, GH #588) shells out to the OS print system — no native deps. `listLabelPrinters({ probeUsb })`: macOS/Linux parse `lpstat -v` (installed queues) and — **only when `probeUsb` is true** — `lpinfo -v` (available `usb://` devices), surfacing the managed queue as its underlying device URI and deduping; Windows runs `Get-Printer` via PowerShell. **GH #771: `probeUsb` defaults to false.** On macOS `lpinfo` issues the admin-only CUPS `CUPS-Get-Devices` op, which pops the OS authorization (admin password) dialog — so the Settings panel lists passively (installed queues, no prompt) on mount and only probes USB on an explicit Refresh, where a credential prompt is expected. `lpstat` is a plain read and never prompts. `printLabel(target, bytes, kind = "brother")` — byte-agnostic, which is why the TSPL printer needed no new transport (the `kind` default keeps every pre-#1042 caller unchanged): a `usb://…` target routes through `ensureManagedQueue()` (idempotent `lpadmin` create/rebind of that KIND's queue, no `-m` → raw queue) then `lp -d <queue> -o raw` with bytes piped to stdin; an installed-queue-name target prints directly; Windows writes a temp file + drives a winspool `WritePrinter` RAW P/Invoke. Per-subprocess 15s timeout (`SIGKILL` on stall); the IPC handler wraps the whole print in its own 30s timeout. `tests/label-printer.test.ts` mocks `node:child_process` and pins: listing parse + managed-queue/lpinfo dedup, direct-queue print (no lpadmin), managed-queue create-then-print for a `usb://` device, idempotent skip when already bound, lp non-zero-exit → reject with stderr, and spawn error → reject. The Windows branch (`process.platform === "win32"`) isn't covered by CI — needs a real Windows host.
- **IPC handlers** (`electron/main.ts`, all `assertTrustedSender`-gated): `label-printer-list-devices`, `label-printer-get/set-public-url`, `label-printer-disable-bidi` (Brother-only), plus the per-printer get/set-device-path + print trio, which is **registered from ONE table**, `LABEL_PRINTER_CHANNELS` — `{kind, storeKey, channels, noPrinterMessage}` rows for `brother` (`labelPrinterDevicePath`, `label-printer-{get,set}-device-path`/`label-printer-print`) and `tspl` (`tsplPrinterDevicePath`, `tspl-printer-{get,set}-device-path`/`tspl-printer-print`). The table exists because these handlers are mirrored BY HAND across `electron/main.ts`, `electron/preload.ts` and `src/types/electron.d.ts` with no compile-time link between the three files, and that mirroring has already drifted in production (#1006 F4); two hand-copied ~50-line print handlers would mean a validation guard tightened on one and missed on the other — a security fix that only half-lands. One loop body means the shared guards apply to both by construction: the `usb://`-or-slash-free-queue-name `devicePath` check (#623), `MAX_PRINT_BYTES = 5_000_000`, **per-byte integer validation via an index loop rather than `Array.prototype.every`** (which skips sparse-array holes, so a 5 MB hole-array would pass and `new Uint8Array` would fill it with `0x00`), and a 30s `withIpcTimeout`. There is deliberately no `tsplPrinterListDevices` — `listLabelPrinters` is printer-agnostic and both pickers share it. `tests/ipc-contract-parity.test.ts` is the permanent drift guard (every channel preload invokes must be registered under `electron/`; every `contextBridge` method must be declared on `ElectronAPI`; both printers must expose a symmetric channel set) and it EXCLUDES `preload.ts` from the literal scan — including it let a typo'd `ipcRenderer.invoke("tspl-printer-prnt")` match itself and pass, i.e. exactly the drift the test exists to catch. The Uint8Array byte stream rides through IPC as a plain `number[]` to sidestep cross-version `structuredClone` quirks; renderer-side `Array.from(bytes)` is O(n) but cheap at the ~270 KB max-label size.
- **Public-URL setting** (`labelPrinterPublicUrl` in electron-store) is required for URL-mode QR codes in packaged Electron — `window.location.origin` is `http://localhost:3456` which scanners on other devices can't reach. Validated server-side in `electron/main.ts`: must be `http(s)`, must not be a loopback host (via the shared `isLoopbackHostname` in `src/lib/loopbackHost.ts`), must have no query string or fragment (raw-input check — bare `?` / `#` slip past `parsed.search`/`parsed.hash`). Renderer-side `isLoopbackUrl(window.location.origin)` shares the same helper to disable URL mode when the dialog detects a localhost origin and no public URL configured.
- **`isLoopbackHostname`** (`src/lib/loopbackHost.ts`) is the single source of truth for "this hostname addresses the local machine". Covers every URL.hostname output we've seen: `localhost` (case-insensitive), DNS absolute-name notation (`localhost.`, trailing dots), 127/8, bare + bracketed IPv6 loopback (`::1`, `[::1]`, uncompressed `0:0:0:0:0:0:0:1`), IPv4-mapped IPv6 loopback in dotted + Node's hex-normalised form (`::ffff:127.x.x.x` and `::ffff:7fNN:YYYY`), and the unspecified-bind addresses (`0.0.0.0`, `::`, `[::]`, IPv4-mapped `::ffff:0.0.0.0` / `::ffff:0:0`). 56-case test suite in `tests/loopbackHost.test.ts` pins each shape end-to-end through `new URL().hostname`. **PR #487 went 12 Codex iteration rounds, mostly on this validator.**
- **Packaged build**: the label printer no longer bundles any native module (GH #588 removed `serialport`/`@serialport/*`/`node-gyp-build`/`node-addon-api` from `electron-builder.yml` and `package.json`) — it shells out to the OS print tools (`lp`/`lpstat`/`lpinfo`/`lpadmin` / `powershell`) which are always present. `npm run electron:rebuild` now rebuilds only `@pokusew/pcsclite` (the NFC native module): `-o @pokusew/pcsclite`. **Linux note:** creating the managed raw queue needs `lpadmin` rights; if it fails the transport surfaces a message telling the user to add the printer in their system print settings first (then it shows up as an installed queue and prints with no `lpadmin`).
- **Customizable label format (GH #592)**: a global `LabelFormat` (`src/lib/labelFormat.ts`, pure + unit-tested) controls QR placement (left/right/off), the stacked text fields (presets + per-field toggles via `composeLabelLines`; since v1.67/#1013 every `LABEL_PRESETS` entry carries a `labelKey` rendered via `t()` — was hardcoded English), curated font family + size (`FONT_STACKS` — no bundled fonts), text orientation (horizontal/vertical), and invert (white-on-black). Persisted by `src/hooks/useLabelFormat.ts` (electron-store on desktop / localStorage on web, mirroring `useCurrency`; JSON under key `labelFormat`/`filamentdb-label-format`). The renderer `renderLabelBitmap`/`renderLabelPreviewDataUrl` take `(filament, qrPayload, format)` and share one `composeLabelCanvas` so preview ≡ print. **Invert keeps the QR dark-on-light** (an inverted QR won't scan) by drawing it on its own white tile. Edited in `src/components/LabelFormatEditor.tsx` with a live preview over a built-in `SAMPLE_FILAMENT`; the editor is NOT Electron-gated (the format applies to the web `.bin` path too). The per-print QR *payload* mode (instanceId vs URL) stays in the dialog. `DEFAULT_LABEL_FORMAT` reproduces the pre-#592 output (QR left + name). No "remaining" field — a printed amount goes stale; scan the QR for the live value.
- **Settings UI**: `src/components/LabelPrinterSettings.tsx` renders only in Electron (`useIsElectron`), mounted from `src/app/settings/devices/page.tsx` (since #801 Settings is tile-based — `src/app/settings/page.tsx` is a tile launcher and the real panels live in per-category sub-pages under `src/app/settings/{ui,network,ai,backup,danger,devices}/`). On mount it lists configured queues passively (`loadDevices(false)` — no `lpinfo`, no macOS admin prompt, #771), and **Refresh** re-lists the same passive way; only **Scan for USB printers** probes (`loadDevices(true)`), additionally enumerating raw `usb://` devices via `lpinfo` — which may prompt on macOS, so that button carries the `scanHint` warning as its title. Badges PT-Touch matches. Public URL field validates through the IPC handler and surfaces the main-process error inline. The `LabelFormatEditor` (#592) is mounted right after it, ungated.

- **Wire-format byte traps** (avoid re-litigating these — pinned in `tests/labelEncoder.test.ts`):
  - `ESC i z` media width: 3.5mm tape rounds to byte 4 (Brother's wire convention); 6/9/12/18/24 round to themselves. `Math.round` covers both.
  - `ESC i M` mode bits: `0x40` enables auto-cut; `0x00` disables.
  - `ESC i K` various-mode flags: bit 3 (`0x08`) = no-chain (feed + cut after the LAST label). With `0x00` (chain mode) the autoCut bit still issues a cut command, but the tape isn't fed through the cutter and the label stays stuck in the head. The encoder ties this to the `autoCut` option: `autoCut: true → 0x08`, `autoCut: false → 0x00`. Don't hard-code either value.
  - Trailer: `0x1A` (print with feed/cut) when `autoCut: true`; `0x0C` (print, no feed) when `autoCut: false`.

**Caveats / known constraints** (post-#588 USB transport):
- **Windows + Linux are implemented but not yet hardware-tested** — only macOS USB is validated end-to-end. The Windows winspool `WritePrinter` RAW P/Invoke and the Linux `lpadmin` managed-queue path both need on-hardware confirmation.
- **The app auto-manages TWO hidden CUPS queues** — `MANAGED_QUEUE = "FilamentDB_Label"` (Brother) and `MANAGED_QUEUE_TSPL = "FilamentDB_Label_TSPL"` — one per `LabelPrinterKind`, for raw `usb://` devices that aren't an installed queue. Both appear in the user's printer list, with distinct `lpadmin -D` descriptions from `queueDescriptionFor(kind)` so they don't read as duplicates, and `isManagedQueueName` checks the `MANAGED_QUEUES` array so both surface as their underlying USB device in the pickers. **The split is load-bearing, not tidiness**: `ensureManagedQueue` REBINDS its queue to whichever device is printing, so with one shared queue name and both printers selected as raw `usb://` URIs, a spool print and a dry-box print overlapping in time would rebind the queue away from each other — and because CUPS delivery is asynchronous (the `lp` job spools after the rebind but drains later) a job could reach the WRONG PHYSICAL PRINTER. Creating a queue needs `lpadmin` rights (fine for admin users on macOS; on Linux, if `lpadmin` fails the transport tells the user to add the printer in their system print settings first, then it shows up as an installed queue and prints with no `lpadmin`).
- **`PRINTER_PATTERN` (`/pt-?p710bt|p-?touch|brother/i`) was deliberately NOT widened to the KNAON**, and an earlier widening was reverted. Its only consumer is the Brother picker, which renders the flag as a "PT-Touch" badge and saves the selection for `label-printer-print` — whose job is Brother RASTER bytes. Badging a Y813BT there actively invited the user to send raster to a TSPL printer. Per-kind badging lives with the TSPL picker (`TSPL_PRINTER_PATTERN = /knaon|y-?813/i`, client-side in `TsplPrinterSettings.tsx`). `printLabel`'s legacy-serial-target message is kind-aware for the same reason — the Brother wording names the old Bluetooth transport, which the TSPL setting postdates entirely.
- **`lpinfo` is scoped to `--include-schemes usb`** — a bare `lpinfo -v` also runs the snmp/dnssd network backends, which probe the LAN ~13s and blow the 15s list-devices IPC timeout (#590).
- **Upgrades from the old Bluetooth/serial setting** (`/dev/tty.*`, `/dev/cu.*`, `/dev/rfcomm*`, `COMn`) are detected and rejected with a "select your printer again" message rather than failing obscurely on `lp -d /dev/...` (a CUPS queue name can't contain `/`).

## v1.48–v1.50: per-spool instanceId (#732)

The 5-byte hex `instanceId` identity moved from the FILAMENT to the SPOOL, so each physical roll has its own durable identity (the value NFC tags carry, QR labels encode, the slicer SSE bus keys on, and inventory CSV round-trips). The filament-level `instanceId` remains as a transitional fallback. Shipped in five phases across v1.48.0–v1.50.0.

- **Schema + migration — Phase 1 (#733, v1.48)**: `ISpool.instanceId: string` on the spool subdocument with `default: generateInstanceId` (`crypto.randomBytes(5).toString("hex")`, 10 hex chars) — `src/models/Filament.ts`. A pre-save hook stamps it; `FilamentSchema.index({ "spools.instanceId": 1 })` indexes it; `backfillSpoolInstanceIds()` migrates existing spools (the first id-less spool of a filament adopts the filament's top-level id — the "carry-over" — the rest get fresh ids). The dbConnect migration block (`src/lib/mongodb.ts`) runs the spool backfill (flag `spoolInstanceIds`) before the legacy filament backfill. `isSpoolInstanceIdTaken(instanceId, excludeSpoolId?, ownFilamentId?)` checks collisions against BOTH other spools' ids AND other filaments' top-level ids (the matcher resolves spool ids first, so a spool id equal to another filament's id would shadow it).
- **Resolve & write by spool — Phases 2 & 3 (#737, v1.48)**: `src/lib/matchFilament.ts` resolves a scanned id against `spools[].instanceId` FIRST (exact-case → CI), returning the matched spool in a new `matchedSpool` field, before the filament-level fallback. `POST /api/nfc/decode` propagates `matchedSpool` + `matchedBy` ("instanceId" | "heuristic"). `src/lib/selectSpoolForWrite.ts` (pure) picks WHICH spool's id a writer encodes: requested spool → first non-retired → first of any → filament-level fallback. The NFC write paths + `GET /api/filaments/{id}/openprinttag?spool=<id>` encode the selected spool's id (and its weight); the desktop scan bus carries the spool uid through to `ScanEvent`.
- **Edit / regenerate — Phase 4 (#739, v1.49)**: `validateSpoolInstanceId` (`src/lib/validateSpoolBody.ts`) — trim, 1–128 chars, `^[A-Za-z0-9._-]+$` (covers numeric Prusament roll ids, auto-gen hex, custom ids). `PUT /api/filaments/{id}/spools/{spoolId}` accepts a validated `instanceId` (409 on duplicate, 400 on bad charset) or `{ regenerate: true }` (mints a fresh id); `POST …/spools` accepts an optional explicit id. ## v1.52: create/link variants from OpenPrintTag (#753)

Connects the OpenPrintTag import path to the variant/inheritance model so a variant can be created from — and stay linked to — an OPT material without the old "import standalone → set parent → hand-delete every inherited field" dance. Two of the issue's three approaches shipped: **C** (link an existing filament) as the foundation and **A** (parent-aware import) on top; the imperative "dedupe on re-parent" **B** was skipped as the only data-mutation-risky one. Builds on the v1.36 re-sync provenance system ([[#607]]).

- **Approach C — link an existing filament (`POST /api/filaments/{id}/openprinttag/link`)**: CSRF-guarded; body `{slug}`. Writes ONLY the linkage (`settings.openprinttag_slug`/`_uuid`) + the `openprinttagSnapshot` provenance via the shared `buildOptLinkUpdate(payload)` (`src/lib/optResync.ts`) — never a field value. So linking can't clobber a user-set or (for a variant) an inherited value: the existing `check` route diffs the variant's EFFECTIVE values, so a field equal to OPT's offer isn't surfaced and a diverged one classifies as `conflict` (user decides). Re-filters `_deletedAt: null` on the write (soft-delete race, mirrors `sync`). 404 `{linked:false, found:false}` when the slug is gone upstream. The bulk OPT import route was DRY'd to use `buildOptLinkUpdate` for its own link write.
- **Approach C UI**: a teal "Link to OpenPrintTag" button on the detail-page action bar, gated on `!filament._hasOwnOptLink` (the inverse of the v1.36 "Check for updates" gate). Opens `src/components/OptLinkDialog.tsx` — a focus-trapped material picker that fetches `GET /api/openprinttag` and renders results only once the user types (capped at 50 — no virtualization needed) → POST link → page refetch (the teal "Check for updates" button then appears).
- **Approach A — import AS A VARIANT (`POST /api/openprinttag/import` gains optional `parentId`)**: imports exactly ONE slug as a variant of the parent (single-slug enforced; parent must exist, be active, and not itself be a variant — `mongoose.isValidObjectId` guard → 400). Pulls only the DISTINCT fields onto the variant via `pruneOptPayloadAgainstParent(payload, parentEffective)` (pure, in `optResync.ts`): every inheritable field whose mapped value EXACTLY equals the parent's effective value is dropped/emptied so the variant inherits it dynamically (scalars/temps → null, the whole-array fields `optTags`/`secondaryColors` → `[]`). Never pruned: `color`/`colorName`/`name` (variant-only) and `vendor`/`type` (required identity — `PRUNE_SKIP_FIELDS`). `diameter` is force-nulled (`mapToFilamentPayload` hardcodes a fake 1.75). The snapshot is built from the FULL offer BEFORE pruning, so a pruned-then-edited field still classifies correctly on a later check. Create-only: a name collision with an existing active row is refused with 409 — it never re-parents/mutates another filament; the unique-name E11000 race recovers to the same 409. Returns the created `filament` in the response.
- **Approach A UI**: on the OPT browser (`src/app/openprinttag/page.tsx`), when exactly one material is selected, an "Import as variant of…" `<select>` (lazily-fetched root filaments — the non-variant rows of `GET /api/filaments`, fetched on first narrow-to-one) switches the import button to variant mode and threads `parentId`.
- **Known limitation (documented + tested)**: when the OPT material has EMPTY `secondaryColors`/`optTags` but the chosen parent has non-empty ones, the variant's `[]` inherits the parent's array (`resolveFilament` reads empty === inherit, GH #106/#477) — e.g. a single-color/no-tag material under a multi-color/tagged parent resolves to the parent's colors/tags. This is the SAME empty=inherit constraint already documented for resync in `OPT_CLEARABLE_ARRAY_FIELDS`; no stored array value resolves to empty while the parent is non-empty, so it can't be fixed without a model-level "no-inherit" sentinel (out of scope). The user can override by editing the variant after import.
- **Tests + docs**: `tests/optResync.test.ts` (pure `pruneOptPayloadAgainstParent` + `buildOptLinkUpdate` cases) and `tests/opt-resync-route.test.ts` (link route + variant import: variant-aware classification, strict-equality prune, collision/parent-validation/malformed-id guards, CSRF). OpenAPI documents the `link` endpoint + the `parentId` import param. New `optLink.*` + `openprinttag.importAsVariant`/`variantParent*` i18n keys (EN/DE in lockstep).

## Calibration rows are never destroyed implicitly (#1101/#1102)

`FilamentForm` rebuilt `calibrations` from form state on every save and dropped any row whose nozzle wasn't in `form.compatibleNozzles`. `[].includes(x)` is always false, so a filament with an **empty tick list lost every calibration** — and empty is exactly what the slicer sync-back leaves: the #859 fallback resolves a nozzle from the GLOBAL catalog and never writes `compatibleNozzles` (pinned by `tests/api-route-correctness.test.ts`). The rows were loaded into state, never rendered (the section was gated on the same tick list, #1102), and destroyed on the next save of any field. Editing a **template** was worst — every inheriting variant lost the row at once. Three other producers reach the same state: `POST /api/filaments/{id}/bambustudio` (writes `calibrations` on the addressed doc regardless of parentage), `src/lib/shareImport.ts` (maps `compatibleNozzles` and `calibrations` independently), and the Orca/Bambu `matchPrinterNozzle` global fallback, which deliberately writes `(printerId, globalNozzleId)` rows where the printer does NOT own the nozzle.

- **`hasCalibrationData` is now the ONLY save-time filter** (`src/lib/calibrationScope.ts`): a row survives iff it still carries a value, so a row the form never rendered keeps its loaded values and persists. Blanking a card remains the delete gesture.
- **PR #358's goal is preserved by VISIBILITY, not deletion.** That commit auto-deleted printer-scoped rows whose printer no longer owned the nozzle, because a row the UI can't show *"would persist forever as an orphan… the data becomes undeletable"*. Correct problem, wrong remedy. `partitionCalibrationKeys` splits stored rows into reachable and unreachable, and the form renders the unreachable ones as an explicit list with a Remove button. **Reachability must mirror every gate in the grid** — ticked nozzle, nozzle present in the LOADED catalog (the card loop `return null`s otherwise), a printer tab that owns the nozzle, and a bed-type tab — because a row that is kept but unrenderable reintroduces exactly the orphan #358 was guarding against.
- **Fail open while the nozzle catalog is loading** (`nozzleOwnership.size === 0` ⇒ reachable). `/api/nozzles` is async; treating an unloaded catalog as "unreachable" would dump every valid per-printer row into the orphan list and invite the user to delete it. This is the PR #358 round-2 P1 posture, relocated.
- **Detail page** gates the section on `calibrationSectionVisible` (ticks **or** rows), and the max-volumetric-speed tile's suppression keys off the same flag — keying it off `compatibleNozzles` would double-render the value in the tile AND the table for exactly the filaments #1102 unhides.
- **Residual, pre-existing:** the sync route writes calibrations with atomic per-entry updates while the form PUTs the whole array, so "never destroy what the server gave us" is relative to PAGE-LOAD time. A slicer sync landing while the edit form is open is still overwritten on save.

## A print job migrates a legacy single-spool filament (#1121)

`POST /api/print-history` against a LEGACY roll — stock on the filament's own `totalWeight`, no `spools[]` subdocument — found nothing in pass 2's spool selection and recorded `spoolId: null` with **no debit**. Analytics counted the grams and the cost (`api/analytics/route.ts` iterates `entry.usage` with no `spoolId` filter) while the remaining weight never moved.

- **Debiting the top-level field is not viable, and this is the reason:** `usageHistory` exists ONLY on a spool subdocument, so a top-level debit has no ledger entry — and GH #621's idempotency is literally "refund only when a matching `usageHistory` entry is actually removed" (`print-history/[id]/route.ts`). Without an entry, an advertised retry after a 409 would refund again, unbounded. `spoolId: null` is also already overloaded: it means "every spool retired, deliberately no debit" (GH #305, pinned in `tests/api-route-correctness.test.ts`). Distinguishing the two would need a new `PrintHistory.usage` field, which costs a snapshot version bump (strict mode strips undeclared keys).
- **So the route MIGRATES instead**: it materialises the roll as a real spool (carrying the filament's `instanceId` forward per #732 Phase 1, so printed labels and NFC tags keep resolving) and nulls the top-level field, exactly as `POST /api/filaments` does. Debit and refund then run through 100% existing machinery — real `spoolId`, real `usageHistory` entry, `debitedGrams`, all three DELETE matcher tiers. Zero schema change, zero snapshot bump. It is also the remedy the app already prescribes (the `/inventory` legacy row links to "Manage on filament →").
- **ORDER IS LOAD-BEARING**: the migration runs in pass 1, saved, BEFORE `spoolSnapshots` is built. That snapshot drives the sequential-fallback rollback, which `continue`s past any spool it has no entry for — skipping BOTH the weight restore and the `usageHistory` strip. A spool created after the snapshot would leave an unrefundable orphan on a rolled-back request.
- **A legacy TEMPLATE is refused** (400, `TEMPLATE_NO_SPOOLS_BODY.message`): inventory belongs on its variants (#605), and the message names the action. **An all-retired filament is NOT migrated** — it has a POPULATED `spools[]`, so it still records `spoolId: null` with no debit, preserving the GH #305 contract. Only an EMPTY array migrates.
- Nothing in the app POSTs to this route; the consumers are the PrusaSlicer / OrcaSlicer forks, which is why a hard refusal was rejected — a slicer mid-print cannot "add a spool" in response.

## v1.68.0: nozzle ticks stop hiding slicer presets (#1021)

Since #872 `filamentToSlicerKeys` derived a `compatible_printers_condition` from each filament's *effective* `compatibleNozzles` ticks. PrusaSlicer evaluates that expression as a hard VISIBILITY filter, so a printer whose nozzle diameter wasn't ticked never saw the preset — silently, with no error and no visible cause — and because variants inherit the parent's tick list when their own is empty (GH #106), one parent's checkboxes could hide a whole color family. The reported asymmetry that pinned it: unlinking a variant made the ex-variant reappear (own empty list → no condition) while the ex-parent stayed hidden. The derivation is gone; the ticks are bookkeeping + calibration scaffolding again. The hard part was everything after the removal, because previous round-trips had already PERSISTED the machine value into each filament's `settings` bag.

- **What's derived now: nothing, on the ordinary path.** See the PrusaSlicer "compatible_printers default" bullet. A nozzle-diameter condition survives ONLY on the per-nozzle calibrated fan-out (`byNozzle.size >= 2`), where the restriction is the point.
- **Why a one-shot DB migration and not an export-time filter.** Both Codex P1 rounds on PR #1022 hit opposite sides of one ambiguity: a *pure* nozzle-only condition in a settings bag may equally be a pre-upgrade **user-authored pin** (the old export preserved any non-empty bag value), so shape alone cannot condemn it. Clearing once, at the DB, is what makes "any condition in a bag is user-authored" true BY CONSTRUCTION afterwards — which is exactly what licenses the export to pass everything through untouched.
- **Provenance test** (`src/lib/legacyNozzleConditions.ts`): `isLegacyMachineNozzleCondition(value, populatedNozzles)` = `LEGACY_NOZZLE_CONDITION_RE.test(value)` **and** byte-equality against `deriveLegacyNozzleCondition(populatedNozzles)` — the historical derivation preserved verbatim, docblocked *"Do NOT 'improve' the formatting — it must keep reproducing the historical bytes."* The regex is only a cheap candidate filter; byte-equality against the row's own effective ticks is the decision. **Accepted residue, stated in both directions**: a user pin byte-identical to the current derivation is indistinguishable and IS cleared (re-enter it and it survives from then on); a machine value whose ticks were edited after the round-trip no longer matches and SURVIVES (visible in the settings bag, hand-clearable). "Strictly better than silently deleting a pin."
- **The runner** — `clearLegacyNozzleConditionsOnce(db, {waitMs, pollMs, staleMs})` is driver-level (takes a `MinimalDb`, not mongoose) so `dbConnect` and the Electron sync service share ONE implementation. **Claim-first + wait + resume + fence**: the marker (`_migrations` doc `_id: "legacyNozzleConditions"`) is inserted before any destructive write so racers serialize on the unique `_id`; a loser polls until the winner completes or `waitMs` expires (`LegacyCleanupInProgressError`); a released or stale claim is taken over via a CAS on the observed `claimedAt`; every acquisition mints a `claimToken` that every later marker write filters on, so a taken-over holder is fenced out at its next record write. Durable per-row observations are written BEFORE any destructive write, and each clear is a per-row conditional `updateOne` filtered on the exact condition value **and** the exact `updatedAt` the scan observed (a row saved between scan and write is left alone even if the user re-pinned byte-identical text). The scan/record/clear cycle repeats until a pass finds nothing new, `MAX_CLEANUP_PASSES = 5`. **Not safe to re-run blindly — it is durable-marker-driven, not flag-driven.**
- **The only migration whose catch RETHROWS** (`src/lib/mongodb.ts`, Codex P1 r7): the others are best-effort and safe to re-run, but this one gates correctness — a request served before the DB reaches a terminal cleanup state could export stale conditions, or author a pin the eventual retry would then legitimately match and clear. So the current request fails too.
- **Hybrid cleans BOTH sides itself.** `electron/sync-service.ts` runs the same helper against the local AND remote DBs before any collection sync (abort flag re-checked between). The remote never runs `dbConnect`, and the cleanup preserves `updatedAt`, so LWW would never propagate a clear. The LWW copy is itself an ingestion boundary, so the filament transform RECORDS but never strips candidates in transit (a parent row lives in the collection being synced; pre-fetched provenance goes stale mid-pass) — they're batched into a durable `_migrations` queue `_id: "legacyTransitClears"` before any clear, with an in-memory `pendingLegacyCandidates` fallback on double failure, and both queues drain at the top of every cycle.
- **Permanent ingestion strip — cleaning the DB once is not enough** (Codex P1 r10): a pre-upgrade fork's sync-back or a pre-upgrade INI re-import keeps re-sending the stamped machine condition, and with the one-shot spent it would re-persist and resurrect the hidden-preset bug. `stripLegacyMachineCondition(settings, target)` (`src/lib/stripLegacyNozzleCondition.ts`) mutates the bag in place, bails when the value isn't the machine grammar, and bails when there are no effective ticks (no provenance ⇒ nothing provable ⇒ keep the value). Call sites: `POST /api/filaments` (the shared-catalog import sends ticks + a stamped condition in one body), the PrusaSlicer fork sync-back in `src/app/api/filaments/[id]/route.ts`, `POST /api/filaments/{id}/orcaslicer`, `src/lib/iniImportApply.ts` (a per-invocation clone of the bag, so one row's tick decision can't leak into a later phase's different target), and `src/lib/bambuStudioApply.ts` (both Bambu routes). Fresh creates on the INI/Bambu paths are deliberately unguarded — no ticks exist to test against. The atlas import carries its own inline driver-level equivalent because its refs point at the SOURCE database. **The fork sync-back's strip is gated on `Object.prototype.hasOwnProperty.call(config, "compatible_printers_condition")`** — `merge.settings` is seeded from the STORED bag, so a partial sync omitting the key must not re-judge and blank a legitimate post-cleanup pin.
- **Snapshot provenance — `CURRENT_SNAPSHOT_VERSION` bumped to 5** with a new top-level `legacyNozzleCleanupComplete`, stamped from the durable marker. Restore calls `rerunLegacyNozzleCleanupAfterRestore(...)`: `true` ⇒ the backup is post-cleanup, so a byte-identical pure nozzle condition in it is a USER pin and only the marker is stamped completed; `false`/absent ⇒ ONE atomic marker conversion (release + clear `processed`, unset `completed`) **before** the process-local flag flips — ordering matters, or a racing `dbConnect` could observe (flag false + completed marker) and flip the flag back — then re-run. A failure of that durable write throws `RestoreCleanupInvalidationError`, which the snapshot route turns into an error telling the user to run the (idempotent) restore again; reporting success would strand restored legacy conditions forever. Pre-#1022 builds reject a v5+ file via the #953 guard rather than silently dropping the flag.
- **Tests**: `tests/legacyNozzleConditions.test.ts`, `tests/stripLegacyNozzleCondition.test.ts`, `tests/import-atlas-legacy-condition.test.ts`, plus blocks in `tests/mongodb.test.ts`, `tests/sync-service-expansion.test.ts` and `tests/snapshot.test.ts`.

## v1.68.1: hardening batch (#1025/#1026/#1028/#1030)

Four independent correctness/security fixes plus the dependency work that unblocked CI. No schema changes, no data migrations.

- **Prototype-pollution guard on the filament PUT (#1026 / PR #1032, GHSA-664h-wqgq-64gw)**: `PUT /api/filaments/{id}` forwards the parsed body verbatim to `findOneAndUpdate`, and its pre-existing injection guard rejects `$`-prefixed keys — but `"__proto__.x".startsWith("$")` is false and the mass-assignment strip above it is an exact-key denylist, so a `__proto__`-DOTTED key reached Mongoose's update casting. Upstream, `Schema.prototype.path()` does an unguarded `this.paths[path]` lookup on a plain object, so `"__proto__"` resolves up the prototype chain to `Object.prototype` itself and `_getSchema` writes an **enumerable** `$fullPath` onto it — leaking into every `for...in` in the process. One unauthenticated request, persistent for the process life. Two layers: `package.json` pins `mongoose: "~9.7.4"` (patched upstream ≥ 9.7.2), and the route calls `assertSafeUpdateBody(body)` (`src/lib/requestGuard.ts`) right after the `$`-operator check — `UNSAFE_UPDATE_PATH_RE = /(^|\.)(__proto__|constructor|prototype)(\.|$)/`, anchored on segment boundaries at both ends so it matches the dotted-path grammar while leaving a field that merely CONTAINS one of the words alone. **Own enumerable TOP-LEVEL keys only** — exactly what `findOneAndUpdate` casts, which is why a slicer setting named `constructor` still rides through the nested `settings` passthrough bag untouched. 400, not a silent drop. Scope was determined empirically: this is the ONLY route that forwards a client-shaped object into an update, so applying the helper elsewhere today would be dead code.
- **`MAX_USAGE_GRAMS = 1_000_000` (#1030 / PR #1033)**: `MAX_SPOOL_HISTORY` bounded how MANY usage entries a spool holds; nothing bounded how BIG one could be. Both write boundaries validated only `Number.isFinite` + a floor, and `Number.isFinite` excludes just `Infinity`/`NaN` — so `{"grams":1e308}` cast, validated and persisted. Analytics sums raw doubles, and once a day's sum overflows to `Infinity` the Hamilton apportionment computes `ideal = (raw / Infinity) * Infinity = 0 * Infinity = NaN` for **every segment of that day**, which `JSON.stringify` renders as `null` — so an unrelated, correctly-sized filament that merely printed on the same UTC day also came back null, violating the numeric contract `public/openapi.json` declares. The 1-tonne bound lives in `src/lib/capUsageHistory.ts` and is enforced with a 400 at `POST /api/print-history` and `POST /api/filaments/{id}/spools/{spoolId}/usage`. Analytics sanitises at **ingestion** instead of the six emit points — `safeGrams(value)` returns 0 for non-number/non-finite/`<= 0`, else `Math.min(value, MAX_USAGE_GRAMS)` — which also covers rows arriving through paths that bypass the routes (snapshot restore, hybrid sync), and renders a clamped row AT the cap rather than vanishing so corruption stays visible. **Deliberately not a schema `max:`** — it would add exactly one covered path over the route caps, still miss hybrid sync, and (Mongoose validating on every later save) would BRICK any spool already holding an over-cap entry. Also deliberately NOT tightened to catch unit confusion (mm ≈ 330,000/kg, mm³ ≈ 806,000/kg both land just under): this constant exists for overflow safety.
- **Bounded NTAG read page (#1028 / PR #1035)**: a Type-2 READ BINARY pseudo-APDU carries the start page in a SINGLE byte, and `Buffer.from(array)` applies `& 0xff` silently — so page 256 emits `ffb0000010`, a read of pages 0–3 (UID, BCC, internal byte, static LOCK bytes, CC). `assembleNtagImage` derived its extent from the **tag-controlled** CC byte and walked `page += 4` with no upper bound, so a CC byte `>= 0x7f` (not `0x80` as the issue's table said — `0x7f` → 1016 bytes → 64 bursts → final page 256; `0x7e` is the last safe value) spliced that head back into the TAIL of the NDEF image. Silent corruption, and since the same assembler backs the post-write verify, a write could verify against those bytes. **No genuine NTAG213/215/216 can trigger it** (the largest legitimate mlen is `0x6d` → final page 220) — it needs a malformed, foreign, partially-written or hostile tag. The arithmetic moved to the pure, coverage-gated `src/lib/ntagPages.ts` (mirroring what #973 did with `ntagVersion.ts`; `electron/` has no test file and this was its SECOND page-arithmetic bug): **`NTAG_MAX_NDEF_BYTES = 1008`, correcting the old 1024** — one Type-2 sector is 256 × 4 = 1024 bytes TOTAL and the data area starts at page 4, so the largest addressable extent is `(256 − 4) × 4`; being off by exactly the 16-byte head is precisely what let the loop run one burst past the end. `ndefBytesFromCc` treats every field as hostile (a head shorter than the CC index → 0, which used to reach `Buffer.alloc(16 + NaN)`). **Two traps stated in the code**: do NOT "fix" this by clamping (`page = Math.min(page, NTAG_MAX_PAGE)`) — that keeps the loop alive and converts the accidental wrap into a permanent re-read of one page, an NFC deadlock; and the zero-progress `if (copyLen === 0) break;` guard is load-bearing, because the wrap to page 0 was what kept data flowing and masked it. Posture: an over-large CC now yields a SHORT image (callers already use the returned `written`), matching the existing NAK-driven `break`.

## v1.69: dry-box labels on a second (TSPL) printer (#1038/#1042/#1043)

Filament DB already printed 24 mm spool labels on a Brother PT-P710BT. v1.69 adds a **second, completely independent label printer** — the KNAON Y813BT on 100 × 150 mm stock — for a different label domain: a **dry-box label** that names the box, lists what's in it (dated), records when the desiccant was last changed, and carries a QR that opens the live inventory view for that box. The contents list is a point-in-time snapshot, which is why it prints with an "as of" date and the QR resolves the live truth. Because the Y813BT firmware turned out to implement TSPL's native text/barcode/QR primitives, a whole 4×6 label is ~600 bytes of ASCII commands rendered from the printer's own font ROM — no rasterizer, no QR library, no native module.

- **Why TSPL, and how the command set was established.** KNAON publishes no command language for the Y813BT. The vendor Linux driver settles it: `/usr/lib/cups/filter/knaon/Filter/rastertolabel` is a fork of CUPS 2.2.7's stock `rastertolabel.c` with a new branch appended at `*cupsModelNumber: 20` (stock CUPS uses 0 Dymo, 0x10/0x11 Zebra EPL, 0x12 ZPL, 0x13 CPCL, 0x20 Intellitech PCL — 20 decimal is new). **`strings | grep` is actively misleading**: every Zebra and Dymo literal is still in the binary as dead code; only the literals the model-20 `StartPage`/`EndPage` reference are real. The driver emits ONLY `BITMAP`, which proves nothing about the firmware (many ODM firmwares ship a raster-only subset) — so `tests/fixtures/tspl/03_probe_full.prn` was printed on hardware and **all nine numbered probe items rendered**, including `BARCODE` (Code 128) and `QRCODE`. Hence native primitives throughout: ~600 bytes off the font ROM versus 812 × 1218 px ≈ 124 KB for the same label rasterized 1-bit at 203 dpi. `bitmap` stays in the `TsplCommand` union for future logo support; no rasterization path exists and none is needed. **Do not re-derive this — the module header records that it cost a printed label.**
- **Emitter (`src/lib/tsplEncoder.ts`, pure — no Node, no DOM).** Returns `Uint8Array`, never `Buffer`, so the sandboxed renderer can import it to drive the on-screen preview from the same document (mirrors `labelEncoder.ts`). `render(doc)` emits `SIZE → GAP → [DENSITY] → [SPEED] → [REFERENCE] → [DIRECTION] → CLS → commands → PRINT sets,copies`; the four bracketed lines are STRUCTURALLY optional (the minimal probe that proves the parser is alive is `SIZE/GAP/CLS/PRINT` and nothing else), and `DIRECTION` is absent from the vendor driver's string table — it works but is unverified on this firmware, and its docblock names it as the first line to drop when diagnosing a job that produces no output. **CRLF framing is mandatory and guaranteed by construction**: every fragment goes through a `line()` helper, and `asciiBytes()` throws on a raw `0x0A`/`0x0D` inside a command — because **an LF-only job is silently discarded by the firmware (no error, no output, no paper movement), so it presents identically to a dead printer**. The exported `assertCrlfFramed(bytes)` does a full both-halves scan (rejecting a bare CR too) and is valid only for bitmap-free jobs, since a binary `BITMAP` payload may legitimately contain a lone `0x0A`; `render()` therefore doesn't call it — it exists to validate jobs from OUTSIDE the emitter, which is what the CLI's `--file` mode does. `mmToDots` rounds half away from zero symmetrically so a negative `REFERENCE` mirrors its positive twin; all four dimensional spec fields go through `Number.isFinite` first (without it `Infinity` satisfies `> 0` and `SIZE Infinity mm,150 mm` was emitted with no error), though a negative `gapOffsetMm` stays legal as a signed alignment nudge. Output is chunked, never `push(...spread)` — spreading a 124 KB raster blows V8's call-stack limit. `qrModuleCount(payload, ecc)` carries byte-mode capacity tables (versions 1–20, all four ECC levels, counting **UTF-8 bytes**) because a `QRCODE` command's printed size is NOT implied by its arguments — the firmware picks the symbol version from the payload at print time, so placing a QR without computing this prints a symbol that silently runs off the stock.
- **The ASCII fold is a data-loss guard, not a stylistic default** (hardware-settled 2026-07-28, `tests/fixtures/tspl/05_codepage_probe.prn`). A probe emitted `°³²äß` at both their latin1 and cp437 byte values, in three blocks — no `CODEPAGE`, after `CODEPAGE 1252`, after `CODEPAGE 437`. **All twelve high-byte rows printed `[` and then STOPPED**; the closing `]` never appeared, while the pure-ASCII control row rendered perfectly. So **a byte ≥ 0x80 inside a quoted `TEXT` literal truncates the string at that point and the rest of the line is silently lost**, and `CODEPAGE` is accepted-and-ignored. Without `toAscii()` a filament named "Grün" prints as "Gr" and drops the rest of its row. `TRANSLITERATIONS` handles what NFD decomposition can't (`ß→ss`, `ø→o`, `°→deg`, `€→EUR`, smart quotes, dashes) plus four space variants — **`GROUP_SPACE` (U+202F) is in there specifically because it is the thousands separator the v1.66 "Space" number format emits**, so it reaches a label through any formatted weight or price. Anything else becomes a visible `?` rather than vanishing. `\p{M}` was deliberately rejected for an explicit combining range: property escapes are ES2018 while the repo targets ES2017, and `tsc` validates regex FLAGS against the target but not regex BODIES — `\p{M}` would typecheck and fail only at runtime. **`sanitizeTsplLiteral()` strips line terminators BEFORE folding, and the order is load-bearing**: the fold maps control characters to `?`, so folding first leaves nothing for the strip to match and the injection guard (a newline in a free-text note terminates the `TEXT` command and hands the remainder to the parser as a new command) degrades into cosmetic mangling. It also substitutes `"`→`'` and `\`→`/`, since escape behaviour is unverified on this firmware.
- **Template (`src/lib/dryBoxLabel.ts`, pure, DB-free, everything injected).** `dryBoxLabel(input, strings = DEFAULT_DRY_BOX_STRINGS)`: `asOf`, `formatDate` and every user-visible string are INJECTED, never read from the clock or locale — reading the clock breaks determinism, and calling `toLocaleDateString` inside would make the same document render differently on the preview canvas and the print head. The template therefore carries no English; `DEFAULT_DRY_BOX_STRINGS` is a CLI/test convenience. `DRY_BOX_SPEC` is 100 × 150 mm (not a true 4×6 = 101.6 × 152.4) because that is what the hardware-verified fixtures declare and they print correctly. **Only the header block is fixed geometry (`DRY_BOX_LAYOUT`); everything below is DERIVED by `dryBoxGeometry(spec, qrPayload)`, because the QR's printed size depends on the payload.** Elements top to bottom: a `BOX` border that grows to clear the QR's FOOTPRINT (not just the symbol) so it never lands inside the quiet zone; the location name in font "5"; a subtitle in font "3" that appends `"  {humidity}% RH"` only when the location carries one; the QR; a `CONTENTS (as of …)` heading + rule; one manifest row per item; a footer rule; the `DESICCANT CHANGED` line; a replace hint in font "2"; and a Code 128 of the box name, inset by its 10-module quiet zone and **omitted entirely when it cannot fit**.
- **The fit helpers, and the "prints fine, never scans" failure class** — four separate review rounds found instances of the same defect, so state the pattern once. `fitQr` iterates ECC `H → Q → M → L` computing `cell = min(8, floor(maxDots / (modules + 2*4)))` — fitting the footprint INCLUDING the quiet zone, not the data area — and takes the first (strongest) ECC reaching `QR_MIN_CELL = 4`. **`QR_MIN_CELL` is a floor, not a preference**: returning a 2- or 3-dot symbol "so something prints" hands the user a label indistinguishable from a working one until they try to scan it, so a payload that can't reach the floor at any ECC **throws**. `fitBarcode` returns null and the barcode is dropped, because a clipped Code 128 has no stop pattern and **scans as nothing while still looking like a barcode**. `fitRowText` measures the **sanitized** string, since several transliterations are length-INCREASING (sixteen `ß` fitted to a 16-char budget printed as thirty-two) — and `dryBoxLabel` sanitizes `qrPayload`/`barcodePayload` ONCE at the top and uses the sanitized string for BOTH sizing and emission, a structural fix so a third measurement site can't repeat it. **Per-font budgets are separate for a reason**: the first physical label truncated the hint 16 characters early with a third of the line unused, because the font-2 hint was budgeted with the font-3 `rowChars`; `dryBoxGeometry` now carries `rowChars`, `nameChars`, `subtitleChars`, `footerChars` and `hintChars`. TSPL `TEXT` neither wraps nor clips — it just runs off the edge — which is why every field is explicitly fitted with a visible `...`. `dryBoxGeometry` throws rather than emitting off-sheet coordinates when the stock is too small or too short, and the contents block is emitted as a UNIT (heading + rule + rows, or none) because suppressing only the rows printed a "CONTENTS" heading on top of the footer.
- **`describeItem`** builds one manifest line: the spool's own `label` when set (it's what's written on the physical roll), else vendor + name + type, deduped. Both dedup checks match **whole tokens** via `tokenized()` (case-fold, collapse non-alphanumerics to spaces, pad so the padding supplies word boundaries), because a bare `includes` silently dropped the MATERIAL — `"Prusa Space Gray"` + `PA` matched the `pa` inside `Space`, likewise `Papaya`/PA, `Sapphire`/PP, `Petrol Blue`/PET — and on a dry-box manifest the material is the one thing a glance needs. **`+` deliberately survives normalisation** (it is a material distinction: collapsing it made `tokenized("PLA+") === tokenized("PLA")`), while hyphens and slashes still collapse so a `PC-ABS` type matches a `PC ABS` name. Vendor dedup matches LEADING whole tokens, not `startsWith` (`"Sun"` vanished from `"Sunset Orange"`); the documented trade-off is that `"Prusa"` + `"Prusament PLA"` now renders redundantly rather than dropping the vendor.
- **`buildLocationDeepLink(base, locationId)`** (`src/lib/labelDeepLink.ts`) → `<base>/inventory?location=<encoded id>`, canonicalized through `new URL(url).href`. Deliberately not a location page (there is no location VIEW route, only `/locations/{id}/edit`) — `/inventory` already answers "what is in this box right now", live. The `.href` canonicalization is not cosmetic: **transliteration is the wrong transform for a URL.** An internationalized public URL ASCII-folded would yield a QR that scans perfectly and points at a domain the user does not own; punycode + percent-encoding is the SAME URL in ASCII, so the emitter's downstream fold becomes a no-op.
- **Transport, queues, IPC, badging** — see the "Label printers" section: no new native module (the transport was already a raw pump, and `lp -o raw` was confirmed on hardware to reach the print head untouched even through a queue carrying the vendor PPD), a SECOND managed CUPS queue to prevent a cross-printer job delivery, the `LABEL_PRINTER_CHANNELS` table + `tests/ipc-contract-parity.test.ts`, and `PRINTER_PATTERN` staying Brother-only on purpose.
- **`Location.desiccantChangedAt: Date | null`** (`src/models/Location.ts`, new; the sibling `humidity` predates this work and is only READ here). Meaningful for `kind: "drybox"`, drives the label's DESICCANT CHANGED line, optional even there. **Both write paths validate the string with `isValidIsoDateString` BEFORE Mongoose casts it** — `POST /api/locations` and `PUT /api/locations/[id]` each return 400 `"desiccantChangedAt must be an ISO date string or null"` — because Mongoose ROLLS OVER an impossible-but-ISO-shaped date rather than rejecting it, so `"2026-02-30"` would silently persist as March 2nd (the same trap the spool date fields hit in GH #372). The PUT adds it to the explicit allowlist (the GH #424 pattern). `toCalendarDate()` in the template re-anchors the stored midnight-UTC value to LOCAL midnight before formatting, or every user west of UTC saw the previous calendar day — the same bug v1.60.1 fixed for analytics day labels.
- **Snapshot consequence — `CURRENT_SNAPSHOT_VERSION` bumped 5 → 6**, and `desiccantChangedAt` added to `DATE_FIELDS` so restore revives it as a `Date`. The bump is argued in place against the instinct not to: an additive nullable field LOOKS like it should degrade gracefully, but a build without the field would ACCEPT the file and its stricter Location schema would silently DROP the date — a "restored successfully" that quietly lost data (v4 exists because exactly that happened to share links). Failing closed via the #953 guard is the established trade-off: a refused restore is recoverable, a silent partial one isn't.
- **UI.** `TsplLabelPreview.tsx` maps the **same `LabelDocument`** to SVG — one layout pass, two painters, so preview and print cannot drift; geometry is exact, `TEXT` uses `textLength` + `lengthAdjust="spacingAndGlyphs"` against a per-font advance table so line length and truncation are exact, the QR is a real symbol at the same ECC (rendered with `margin: 0`, because the document's x/y is already the symbol origin and the template reserves the quiet zone as separate whitespace), and `BARCODE` is deterministic stylized stripes of the correct overall width — explicitly not a scannable Code 128. `PrinterDevicePicker.tsx` is the extracted, deliberately dumb device-radio list both panels share (per-picker `radioName` so two radio groups on one page don't merge; `isBadged`/`badgeLabel` keep badge semantics with the owning panel; `renderRowExtra` carries the Brother-only BiDi warning). `TsplPrinterSettings.tsx` is the Brother panel's sibling — same GH #771 posture (`loadDevices(false)` on mount and on **Refresh**; only **Scan for USB printers** probes with `loadDevices(true)`), own store key, own badge pattern, a **Test print** that renders a minimal known-good job through the REAL pipeline, and (in BOTH panels) an amber stale-selection banner when `selectedPath` matches no listed device, since with no devices left the picker isn't rendered at all and the selection would be invisible AND unclearable. `PrintDryBoxLabelDialog.tsx` mirrors `PrintLabelDialog` but is data-only glue; three things not to re-litigate: (1) **the manifest is fetched HERE, unfiltered** (`GET /api/spools/by-location`, then find the group) and never taken from the calling page's rows — the inventory page's `group.spools` is the VISIBLE subset, and printing that under an active filter asserted a partial list as the box's full, dated contents; (2) **`publicUrl` is three-state** (`undefined` pending / `null` not-configured / string), because collapsing pending into null let a fast manifest fetch enable Print before the saved URL arrived, **baking localhost into a physical label** for a user who HAD configured one; (3) there is no fallback payload mode, so with a loopback origin and no public URL the dialog warns but still prints — name + barcode still identify the box.
- **Entry points (two, both gated on `kind === "drybox"`)**: a printer-icon button in each `/inventory` location group header (additionally gated on `groupBy === "location"` — a group must BE a location), and a "Print label" action on every drybox row of `/locations`. The second exists because `/inventory`'s groups are built FROM SPOOLS, so a newly created or just-emptied dry box had no print entry point at exactly the moment you most want to label it; the dialog fetches its own manifest and an empty box prints `(empty)`. Both mount via `next/dynamic({ ssr: false })` so the TSPL emitter + `qrcode` preview stay out of the page bundle. **Scan-back on `/inventory`**: `?location=<id>` is read once from `window.location` (`deepLinkHandledRef`, no `useSearchParams` → no Suspense boundary, the same pattern as the detail page's `?spool=`), **forces `groupBy = "location"`** (under a persisted type/vendor/none grouping the section ids are bucket values, not location ids, so a scanned QR found no target and silently did nothing), un-collapses and rings the group; the scroll is a SECOND effect because a same-tick `requestAnimationFrame` can fire before the `setGroupBy` commit. An id matching no group shows an info toast rather than no-opping — a printed QR pointing at silence reads as "the app is broken".
- **Bring-up CLI**: `npm run label:tspl` → `scripts/print-tspl.ts`. `--file <path.prn>` sends a raw job unchanged (CRLF-validated first via `assertCrlfFramed`) and `--demo` renders a sample label through the REAL pipeline; the two are mutually exclusive and one is required. `--printer <target>` prints for real via `printLabel(..., "tspl")`; otherwise the bytes go to `--out` (default `/tmp/label.prn`) and the decoded job text is echoed for inspection.

## v1.70: a parent filament is a TEMPLATE (#605 / PR #1049)

Before v1.70 a "parent" was structurally identical to its variants — it could hold its own color, its own spools, its own weights — which made the whole parent/variant model ambiguous: users couldn't tell whether the parent was a *category* or just the first color they happened to enter, and half the app counted a parent's leftover spools while the other half ignored them. GH #605 settled it: **once a filament has variants it is a TEMPLATE — an abstract product line carrying shared spec (temperatures, drying, density, tare, net weight, secondary colors, tags) and nothing per-roll.** Templates are colorless and hold no inventory; every write path that could re-attach a color, a total weight, a low-stock threshold or a spool to a template now strips it (and says so) or refuses it; and the moment a filament BECOMES a template the app stops and asks, then MOVES the parent's own color/colorName/spools/inventory onto a newly created sibling variant rather than orphaning them. **Enforcement is forward-only** — legacy parents that already carry state are left alone and given an explicit one-click "Convert to template" action instead of a silent bulk migration (decision 4 on the issue).

- **Template-ness stays DERIVED, never a schema flag.** `hasVariants(FilamentModel, id)` is the single test; a soft-deleted variant doesn't count. A variant can never be a template (no nested inheritance). What a template legitimately KEEPS: `spoolWeight` / `netFilamentWeight` (spec — see below), `secondaryColors` and `optTags` (both inheritable per GH #477, so the shared multi-color set belongs on the template), and every other inheritable scalar.
- **`TEMPLATE_STRIP_FIELDS` = `totalWeight`, `color`, `colorName`, `lowStockThreshold`** (`src/lib/templateStrip.ts`). **Strip, don't reject**: a slicer preset — like a stale edit form — echoes the promoted-away color back verbatim on every save, and a 4xx would break the whole sync for a value the user never re-entered (and would brick parent edits entirely, since the form resubmits every seeded field). **An EXPLICIT `null` passes through** (`stripTemplateFieldsForWrite` filters on `setBody[f] != null`): clearing a legacy parent's leftover value is legitimate cleanup, and blocking it would freeze exactly the pre-#605 state the model migrates away from. **`hasVariants` is only queried when a field actually offends**, so the common no-op sync costs nothing extra. **The strip MUST be called inside `runExclusive(filamentLockKey(id), …)` together with the persisting write** (review P1-c): decided-then-written across a gap, a `totalWeight` PUT racing a first-variant promotion could pass the check while the target was still a standalone and land AFTER the promotion cleared it, re-materialising inventory on a fresh template. Reported, never silent: `_strippedTemplateFields` on the per-id routes (`PUT`+`POST /api/filaments/{id}`, `…/orcaslicer`, `…/bambustudio`, and the Bambu bulk update phases), a per-row note in `errors[]` on the bulk importers (`upsertIniFilament`, `upsertImportRows`, the OPT import's conditional backfill). **`POST /api/filaments/import-atlas` carries its own INLINE MIRROR** — hand-rolled for per-field human-readable notes and because it ALSO guards `spools`; its comment says to keep it in lockstep, so a future field added to `TEMPLATE_STRIP_FIELDS` must be added there by hand. One derived-null subtlety on the PrusaSlicer sync-back: slicers send only a hex, so the route synthesises a `colorName: null` clear alongside a color write (GH #885) — when the color write is stripped that synthesized null is deleted too, or a template holding a legacy pair would keep the color but lose the name.
- **`parent_promotion_required` — the 409 confirmation contract.** Trigger: this request would mint the **FIRST live variant** of a parent that still CARRIES state — `parentPromotionState(parent).needed`, i.e. a non-empty stored `color` (**including the historical `#808080` gray default**, which the pre-#605 form stamped on everything and which renders as the filament's color, so it moves like any other), OR a non-blank `colorName`, OR `spools.length > 0`, OR `totalWeight != null`. From the second variant on nothing gates. THREE emitters share `promotionRequired409Body` byte-for-byte: `POST /api/filaments` with `parentId` (via `createVariantGated`), `PUT /api/filaments/{id}` when the body introduces/changes `parentId` (via `gateFirstVariantAdoption`), and `POST /api/openprinttag/import` in variant mode. **Retry contract**: repeat the identical request with `promoteParent: true` — a control flag, never a schema field (both the create and PUT routes capture it and `delete body.promoteParent` before anything else touches the body). **`POST /api/filaments/{id}/restore` runs the same gate but has NO confirmation path (#1103)** — see the restore bullet below; it emits a different code on purpose, and a client that retries on `parent_promotion_required` must not include it. **The gate runs LAST**, after every other guard, so a 409 means "this request would succeed, but it has a side effect on a second document you must opt into". **Fail-fast before the irreversible bit**: with no transactions available, `gateAndPromoteInLock`'s `beforePromote` hook pre-checks the requested name (409 `name_taken`) and dry-runs `new FilamentModel(body).validate()` on the create path, and re-checks the ADOPTED document's liveness on the PUT path (404 `target_not_found`) — the unique-name constraint is a partial INDEX, not a validator, so a doomed reparent+rename would otherwise E11000 *after* the promotion. Any abort leaves the parent completely untouched. **Both pre-lock facts are re-asserted in-lock** from a fresh parent snapshot: a vanished parent → `parent_not_found`, a concurrently re-parented one → `parent_is_variant` (otherwise the gate would mint a grandchild). **Lock-ordering trap (PUT only)**: the gate holds the PARENT's key while the PUT's write section holds the TARGET's; they are strictly sequential and never held together, because two opposing re-parents (A→B and B→A) acquiring both in opposite orders would deadlock — the residual window is deliberately left open, since its worst case is a template still carrying legacy state, the pre-#605 shape the app already tolerates and "Convert to template" recovers. **Threshold-only parents do NOT gate**: `orphansThresholdOnFirstVariant` returns `clearOrphanedThreshold: true` instead (a promotion that moves nothing isn't worth confirming) and the caller clears the now-dead threshold AFTER its own write succeeds — parent state change last. A *carrying* parent returns false there on purpose, because its promotion moves the threshold with the inventory.
- **What promotion moves, and what stays.** `performParentPromotion` copies `color`, `colorName`, `totalWeight`, `lowStockThreshold` and the whole `spools` array onto the new variant, then `completeParentPromotion` clears exactly those five on the parent (`spools: []`). `lowStockThreshold` moves because it alarms on the weight being moved — left behind it would fire "low stock" forever against an empty template while the variant holding the actual rolls has no threshold. **`spoolWeight` and `netFilamentWeight` deliberately do NOT move (GH #1048)**: they are SPEC — the product line's tare and nominal net weight — not inventory, and they stay on the template where every variant inherits them (both are in `resolveFilament`'s `INHERITABLE_FIELDS`; the promoted variant leaves its own blank so inheritance resolves them). This is what makes #1048's recommended workaround possible: set the net weight on the parent and the whole family gets a remaining-percentage denominator. **The variant body is built explicitly, never spread from the parent**, so server-owned identity can't leak (its own `instanceId`, its own `syncId`, `diameter` pinned `null` so the schema's 1.75 default can't override a non-1.75 parent). **Spool subdocuments move VERBATIM — both `_id` AND `instanceId` preserved**: a subdoc `_id` only needs uniqueness within its owning document and the parent's copies are cleared in the same operation, so reuse is safe and every persisted `(filamentId, spoolId)` reference keeps its `spoolId` half valid.
- **External references follow the spools** (`remapExternalSpoolRefs`, via `updateMany` + `arrayFilters`): `PrintHistory.usage[].filamentId` and `Printer.amsSlots[].filamentId` for entries/slots whose `spoolId` is in the moved set, **plus** filament-only "Any spool" AMS dedications (`filamentId` = parent, `spoolId: null`) **unconditionally, even when no spools moved** — an AMS slot is a FORWARD-looking assignment and the template will never hold inventory again, so "any spool of the parent" is permanently unsatisfiable there. **Deliberate asymmetry**: `PrintHistory` rows with `spoolId: null` are NOT remapped, because history is a BACKWARD-looking record of what was consumed under that name at the time. The models are INJECTED (`PromotionExternalRefModels`), never imported, because `promoteParent.ts` is imported by client components for `parentPromotionState` and a static model import would drag Mongoose into the client bundle — `EXTERNAL_REFS` lives in the server-only `createVariantGated.ts`.
- **Ordering + crash posture — the four-step protocol** (no transactions on standalone mongod): **(0) marker** — `$set: { promotionInFlight: { token, at } }` on the parent, non-destructive and trivially reversible (a marker already present from a run that crashed between its own steps 0 and 1 has its token REUSED rather than stacking a second); **(1) copy** — create the variant carrying `promotedByToken: token`; **(2) remap**; **(3) complete** — ONE parent write that clears the five moved fields AND the marker atomically, so a parent can never be cleared-but-marked or unmarked-but-still-carrying. **Copy first, clear last**: a crash between steps leaves a parent that still carries its legacy state (recoverable) rather than data loss; a crash after the copy leaves the spools momentarily on BOTH documents, but every external reference still resolves against the parent, so nothing dangles. **`$inc: { __v: 1 }` in `completeParentPromotion` is load-bearing** (verified by repro): overwriting the spools array via `save()` would bump the version key, so this raw `updateOne` must too — without it, a hydrated doc loaded before the promotion that modified a spool positionally (the print-history debit/refund saves, the usage route, a CSV import's update bucket) would still match its `__v` in `save()`'s version filter and **re-materialize a phantom spool fragment onto the freshly-cleared template**. With the bump those stale saves fail as `VersionError`, which those callers already map to their designed 409-retry / failed-bucket paths.
- **The resume marker (`promotionInFlight` / `promotedByToken`)** — new `Filament` schema paths, declared for real because strict mode strips unknown keys and an undeclared `$set` would silently no-op; no dedicated index (resume lookups filter on the already-indexed `parentId` first). **Server-owned**: both `POST /api/filaments` and `PUT /api/filaments/{id}` delete them AND sweep every key starting with `promotionInFlight.` / `promotedByToken.` — the dotted sweep matters because the PUT body feeds `findOneAndUpdate`, where `promotionInFlight.token` is a live update path the exact-key deletes would miss. **Why the pair exists**: the earlier heuristics (spool-subdoc-`_id` overlap; deterministic name + full carried-set equality) are RETIRED, because value equality is not record identity and the no-spools heuristic could adopt a legitimate lookalike child and clear the parent's fields without creating the sibling that should have received them — losing an inventory record. `findPartialPromotionVariant` now requires PROOF: the parent's `promotionInFlight.token` paired with a LIVE variant whose `promotedByToken` equals it, a pair only steps 0+1 of this protocol can produce. A marker on a parent whose promotion state no longer gates is stale by construction, so `clearStalePromotionMarker` drops it lazily on the next gate or `/promote` pass and never resumes off it. `resumePartialParentPromotion` is callable on its own because the detector inside `performParentPromotion` is unreachable from the gate's RETRY path — after a partial promotion the parent already HAS a live variant, so a retried request lands in the "already a template" branch and would skip the promotion entirely. **No confirmation gating on resume**: the marker proves a confirmed promotion started, and resuming moves nothing new. Whole-doc copies (hybrid sync, snapshot restore) carry the marker verbatim like `syncId`.
- **`template_no_spools` — the 400.** `pushSpoolWithTemplateGuard` (`src/lib/spoolTemplateGuard.ts`) is check-push-recheck-compensate: pre-check → refuse with nothing written; atomic `$push`; re-check, and if the filament BECAME a template during the push, `$pull` **exactly** the spool just added — located via the `instanceId` the route always stamps, so a concurrent writer's subdoc can never be pulled by mistake. If the process dies between the push and the re-check the spool survives on the template, the same enforce-forward posture as a legacy parent's pre-#605 spools. `options.extraFilter` merges extra conditions into the atomic push filter (the Prusament importer needs its per-filament spool cap `$expr` and, on the name fallbacks, a `name` pin in the same atomic write). Emitters: `POST /api/filaments/{id}/spools`, the three push sites in `POST /api/prusament/import`'s add-spool action (all byte-identical), and `POST /api/spools/import` per row (using `TEMPLATE_NO_SPOOLS_BODY.message` as the row's `error` string). **The CSV spool import splits create vs update**: a row that would CREATE a spool on a template fails; a row whose `spoolId` matches an existing subdoc is still allowed, so a legacy template's pre-#605 spools stay editable. That check runs BEFORE `resolveLocationId` so a failed row leaves no auto-created Location behind, and its per-request `templateCache` is advisory only — the save loop re-checks `hasVariants` INSIDE the per-filament lock before persisting any bucket that appended spools, failing the whole bucket on a trip (all its rows share one `save()`).
- **The bulk FILAMENT importer has a NARROWER gate.** `firstVariantGateInfo` skips a row that would surface the first live variant of a parent holding its own **inventory** (spools or `totalWeight`), with a per-row reason, but **deliberately does NOT gate on color/colorName** — the schema defaults `color` to `#808080`, so every parent the same batch just created from a CSV row without a Color cell would "carry" a color it never had, and gating on it would reject the variant rows of every parent+variant round-trip (the #379/#951 export→re-import flows this importer exists for). A color-carrying parent gaining variants is the tolerated legacy shape; stranded INVENTORY is what #605 forbids.
- **`POST /api/filaments/{id}/promote` — "Convert to template"** (CSRF-guarded, no request body read). 400 `"Invalid filament id"`; 404 when no live filament matches; **400 `not_a_template`** when the target is itself a variant OR has never had a variant that still exists — **TRASHED variants COUNT here (#1103)**, unlike everywhere else that asks "is this a template", because restore now refuses and points at this action, so requiring a LIVE variant would make that advice unactionable and the family unrestorable (`hasVariantsIncludingTrashed`; `_purged` variants still don't count — a permanent delete is a one-way tombstone, so such a parent really is a standalone again). The promotion copy's name also reserves this parent's non-purged TRASHED children via `alsoTakenNames`: they are absent from the partial unique index, so without it the copy could take a tombstoned sibling's exact name and that sibling would then fail restore's active-name conflict check — the conversion would promise to unblock the family and not deliver; **400 `nothing_to_convert`** when `parentPromotionState().needed === false` (also lazily clearing a stale marker on the way out); **200 `{ variant, parent, resumed }`**, where `resumed` reports that this call ADOPTED an interrupted earlier promotion's partial copy. The whole read→guards→promote sequence runs inside `runExclusive(filamentLockKey(id))` with the snapshot fetched INSIDE the lock (review P1-b), so two overlapping `/promote` calls serialize and the second takes the `nothing_to_convert` exit instead of minting a duplicate `" (2)"` copy.
- **The auto-created variant's name**: `promotionVariantBaseName` → `` `${parentName} — ${colorName.trim()}` `` or `` `${parentName} — Original` `` — note the **em dash surrounded by spaces**. It is a **stored record name, not a UI string, and is deliberately NOT translated** so the record reads the same in every locale. `resolvePromotionVariantName` resolves it against the partial unique index (first free of `base`, `base (2)`, …); the `alsoTaken` set lets the caller reserve a name that isn't in the DB yet — the create path passes the REQUESTED variant's name and the PUT path the adopted document's post-rename name, so the promotion copy can never squat on it.
- **`filamentMutex` — what it serializes and why** (`src/lib/filamentMutex.ts`). `runExclusive(key, fn)` chains `fn` behind whatever holds `key`; independent keys never wait on each other. The template guards are all check-then-act and standalone mongod offers no transactions, so two overlapping requests on the same family could each pass a check against pre-write state. **PROCESS-LOCAL by design**: single-process Next.js server (standalone / Electron-embedded — no serverless, no replicas), so a module-level singleton `Map` IS the whole coordination domain; the compensating guards (`spoolTemplateGuard`'s re-check + `$pull`, `/promote`'s `nothing_to_convert` re-derivation) stay as defence-in-depth for out-of-process writers. Chains never leak: the tail promise never rejects (rejections are reflected to the caller only), so a thrown section can't poison the queue, and the key's entry is deleted once the last queued section settles. **`filamentLockKey(id)` lowercases a 24-hex ObjectId string** — MongoDB treats hex ObjectIds case-insensitively but `Map` keys are byte-exact, so a request addressing `507F1F…` would otherwise serialize on a different key than the `String(doc._id)` the create path uses, silently bypassing the mutex for the same family.
- **Templates are colorless to the OpenPrintTag re-sync loop too.** `diffOptFields` gained `options.excludeColor`, and BOTH `GET …/openprinttag/check` and `POST …/sync` derive it from `hasVariants` so check and sync agree exactly on the offered set (a sync naming `color` for a template falls out of `offered` and gets the ordinary 400). The **sync** route derives it IN-LOCK — un-serialized, a first variant created between the check and the write would promote the parent to a colorless template and the sync would re-attach a color to it; the **check** route deliberately doesn't take the lock (read-only). `secondaryColors` stays offered (inheritable, GH #477) and `colorName` isn't OPT-managed at all, so `color` is the only key this drops. Product effect: one OPT link on the parent updates every property of the whole family EXCEPT color.
- **The color-clearing fix (the other half of #605).** Three pure helpers in `src/lib/filamentColors.ts` consumed by `FilamentForm`: `seedFormColorHex(stored)` (a stored `null` seeds `""`, so editing a deliberately-cleared filament doesn't resurrect the gray sentinel), `normalizeColorHexInput(raw)` (returns `""` when no hex chars remain — **pre-fix an emptied box normalized to the dangling `"#"`**, which the submit path forwarded verbatim and the `#RRGGBB`-or-null model validator rejected, so the UI had no way to produce a null color even though the error message promised one), and `submittedColorValue(color, optTags)` (coextruded → `null`; cleared or incomplete → `null`; otherwise verbatim). When `form.color === ""` the `<input type="color">` — which cannot render an empty value — is replaced by a hatched placeholder button, with a **hidden `<input type="color">` mounted unconditionally** behind it so the native picker dialog it opens doesn't close the instant the first picked value flips the branch.
- **Restore REFUSES rather than restructuring (#1103, v1.76).** `POST /api/filaments/{id}/restore` runs the same first-variant gate but answers with **409 `parent_must_be_template_first`** (`restoreBlockedByTemplateBody` in `src/lib/createVariantGated.ts`) — deliberately NOT `parent_promotion_required`, because that code means "repeat with `promoteParent: true`" and here repeating changes nothing; a client matching on it would loop. A `promoteParent` flag in the restore body is IGNORED. **Why**: creating a variant is the user building something new, so trading a confirmation for a restructure is fair there; restore is the user asking for data *back, exactly as it was*, and "Restore all" over a pre-#605 family used to fire one modal per variant whose only "yes" rewrote the family (four variants back as five, the parent stripped) and whose "no" left that variant permanently unrestorable. **Silently allowing it is worse and was rejected**: `_deletedAt` is the entire tombstone, so there is no durable record that the family "used to look like this" — the same relaxation lets a parent that legitimately re-acquired a color while variant-less become a carrying template with live variants (the ambiguous shape #605 exists to prevent, created fresh), with that color then permanently unclearable (the form hides the editor but resubmits the seeded value; `templateStrip` only lets an explicit null through). So the restructure stays mandatory and stays the user's decision — it moves to "Convert to template" on the parent, once for the whole family. The refusal message is composed from `parentPromotionState` (which now also reports `hasColorName` / `hasInventoryWeight`) so it names what the parent ACTUALLY holds, and it deliberately does NOT predict the new variant's name: the gate resolves that against active rows while `/promote` also reserves trashed children, so the two can legitimately disagree.
- **Self-healing printed labels** (`src/lib/spoolDeepLink.ts`). A printed label's QR encodes `/filaments/<filamentId>?spool=<spoolId>` permanently, but a promotion moves a spool to a different document while its subdoc `_id` stays valid. `decideSpoolDeepLink(search, spoolIdsOnDoc)` → `none` | `highlight` | `resolve`; on `resolve` the detail page fetches `GET /api/spools/{spoolId}` (a global `spools._id` lookup) and `router.replace`s to `healedSpoolDeepLinkHref(...)` — the true owner's page with the ORIGINAL query string carried over verbatim, so the keyed remount highlights the spool. Returns `null` (no navigation) when the spool exists nowhere (preserving the pre-existing quiet posture) or when the owner IS the addressed document (loop guard). **This heals ALL stale labels, not just promotion-moved ones.**
- **UI wiring.** On the detail page, when `isParent` the whole Spool Tracker section (including the NFC/scale weight-update paths inside it) is replaced by a template note, and when `parentPromotionState(filament).needed` is additionally true an amber hint + **Convert to template** button appear — **the client uses the SAME predicate as the server's gate and the `/promote` route**, so the button shows exactly when `/promote` would do something rather than 400 `nothing_to_convert`. `FilamentForm` (`isParent` prop) hides the color + color-name editors and the two INVENTORY inputs (initial weight, low-stock threshold) while KEEPING net filament weight + empty-spool weight visible as shared spec; the multi-color editor stays. **The untouched seeded values are still resubmitted verbatim** — which is precisely why the PUT must strip rather than reject, and why a legacy parent's stored color survives editing until the user explicitly converts. The confirm-and-retry flow is THREE copies of one shape (`filaments/new`, `filaments/[id]/edit`, `openprinttag`): 409 → `confirm(...)` → retry with `promoteParent: true`; a decline writes nothing. **`trash` is NOT one of them since #1103** — it shows the refusal instead (translated via `trash.restoreBlocked`, interpolated with `parentName`, because the server composes its `message` in English and this is the user's only recovery instruction). The detail page additionally offers **Convert to template** above the spool tracker when the row is NOT a live parent but `_hasTrashedVariants` is set and `parentPromotionState().needed` — the shape restore refuses on, which would otherwise render as a plain standalone with no such action. The shared-catalog importer (`share/[slug]`) deliberately does NOT retry — a bulk import can't confirm per-parent promotions, so a gated variant row fails loudly with the 409's human `message` and the recipient converts the parent first. The mobile app is unaffected (it has no create-spool call and `createFromTag` sends only name/vendor/type overrides, so it can reach neither the 409 nor `template_no_spools`).
- **Shipped alongside**: #1040/PR #1045 (high-flow disambiguation in the per-nozzle exported condition — see the PrusaSlicer fan-out bullet), #1041/PR #1046 (filament-side AMS slot assignment writes `filamentId` too — see the v1.21 section), and **#1048/PR #1051**: `getRemainingDisplay(f)` in `src/lib/inventoryStats.ts` returns a three-tier result — `{kind:"bar", pct}` when the percentage exists, `{kind:"grams", grams, missing}` when only grams do (`missing` ∈ `"net" | "tare" | "both"` picks the tooltip that names the RIGHT missing weight), `{kind:"none"}` otherwise. The percentage needs `netFilamentWeight` as its denominator; the grams need none. A fabricated denominator was explicitly rejected — defaulting to 1000 g mislabels 500 g / 750 g / 2.3 kg spools. This is the feature that pairs with the spec-vs-inventory split above: set the net weight on the template and every color variant gets its bar.

## v1.72: opt-in spool-shaped mutation responses (#1027)

The response-side companion to the v1.67 #1005 projection sweep. The five spool-mutation routes (`POST /api/filaments/{id}/spools`, `PUT`+`DELETE …/spools/{spoolId}`, `POST …/usage`, `POST …/dry-cycles`) historically return the WHOLE filament document — every spool's `photoDataUrl` blob (≤5 MB each) + full `usageHistory` — for writes that change one scalar. They now accept **`?shape=spool`**:

- **`shape=spool`** → `{ spool: <the affected spool, complete> }` (its own photo/ledger stay — the detail page renders them; the win is dropping the N−1 sibling spools). The DELETE returns `{ deleted: true, spoolId }` (the post-`$pull` doc no longer contains the spool). The POST locates the created spool by the `instanceId` the route always stamps (the fresh `_id` is minted by the `$push` — same technique as `pushSpoolWithTemplateGuard`'s compensation branch).
- **No param** → the full document, **byte-identical to pre-#1027** — LOAD-BEARING for shipped mobile builds (EAS-distributed, updated out-of-band from the desktop), whose `handleSpoolUpdated` reads `.spools` off the body and would blank the spool list on a shape change.
- **Unrecognized value** → **400** (`INVALID_SHAPE_MESSAGE`), so a typo can't silently fall back to the multi-MB default.

Pure helpers in `src/lib/spoolResponseShape.ts` (`parseSpoolResponseShape`, `findSpoolById` — String()-compares `_id` because lean docs carry ObjectId instances — and `findSpoolByInstanceId`). All first-party callers opt in: the detail page's six handlers merge/append/filter the affected spool into local state instead of wholesale-replacing `spools` (`mergeSpoolIntoState`); the home list's `moveSpool` + `/inventory`'s `updateSpool` never read the success body, so for them the param is pure bandwidth. **Mobile handles BOTH shapes at runtime** (`SpoolMutationResponse` in `packages/mobile/src/lib/types.ts`): a freshly-updated phone routinely talks to an older desktop that ignores the unknown param and returns the full doc — `runWrite` discriminates on `payload.spool` vs `payload.spools`, and the usage-log authoritative-weight refresh reads `res.spool ?? res.filament.spools.find(...)`; the returned `totalWeight` stays GROSS (tare-inclusive) because that refresh subtracts the tare itself. OpenAPI: `components.parameters.SpoolResponseShape` + `oneOf` responses; the spool subdoc schema was extracted to `components.schemas.Spool` (previously inlined under `Filament.properties.spools.items`). Tests: `tests/spoolResponseShape.test.ts` (pure) + `tests/spool-response-shape-route.test.ts` (all five routes × both shapes + strict-400 + sibling-blob-exclusion + template-guard interplay); `tests/spool-remaining-weight-route.test.ts` remains the default-shape canary.

## v1.73: "Next #" spool roll-number suggestion (#1060 / PR #1061)

The spool `label` is free-form, but the community convention — and the reporting user's 200+ roll inventory migrated from Spoolman — uses it as an incrementing PHYSICAL roll number, often written on the spool itself. A **Next #** button beside the label field on the detail page's two Add-Spool render sites pre-fills the next one.

- **`GET /api/spools/next-label`** → `{ next, max }`: the highest numeric label anywhere plus one (`next` is `1` when nothing parses; `max` is null then). No params, no request body.
- **The query DELIBERATELY filters nothing** — `Filament.find({}, { "spools.label": 1 })`, no `_deletedAt`, no `_purged`, no `retired`: the opposite of every other spool read in the app. Roll numbers are physical and permanent, so a number on a trashed filament's spool must never be handed out again (restoring that filament would collide) and a retired spool's written number is still on the shelf. Skipping past numbers the user might think are free is the safe direction. The label-only projection follows the #1005 posture — this must never stream photo blobs or usage history. Read-only GET, so no `assertSameOriginRequest` (the guard covers mutating verbs, #360); the optional bearer gate in `src/proxy.ts` applies automatically.
- **`computeNextSpoolLabel` (`src/lib/nextSpoolLabel.ts`, pure + DB-free)**: a label counts only when, after trimming, it is ALL digits (`/^\d+$/`), so `"A12"`, `"12a"`, `"1.5"`, `"-3"` and `"1e3"` are ignored rather than half-parsed; leading zeros are stripped (`"0042"` → 42). **Acceptance is by VALUE (`Number.isSafeInteger`), not by digit count** — a digit-count cap made the generator and the parser disagree at the boundary: with max `999999999999999` the suggestion was the 16-digit `1000000000000000`, which a 15-digit guard then rejected on the next request, so after creating that spool **the same number was suggested forever**. Value-based acceptance means every suggestion this function emits is re-accepted by it, while a 200-digit "number" parses past the safe range and can't poison the max. `next` is capped at `Number.MAX_SAFE_INTEGER`.
- **Reserves nothing.** Suggestion-only: the client pre-fills an editable field, and two concurrent readers can receive the same value (accepted on the issue — single-admin reality, and the human edits the field anyway).
- **Client** (`src/app/filaments/[id]/page.tsx`): one shared `useCallback` used by BOTH duplicated Add-Spool render sites so behaviour can't drift. It **snapshots the label at click time** and applies the response only when the field still holds that value — if the fetch is slow and the user types or pastes meanwhile, the suggestion must not clobber the newer input. **The field stays enabled during the fetch on purpose** (disabling would trade the race for an input lockout); only the button is disabled and shows `…`.

## Mobile scanner app (packages/mobile)

An Expo / React Native companion scanner — a deliberately **thin client** that does no business logic: it forwards scans + edits to the desktop/web server's REST API and renders the responses (field mapping lives server-side).

- **Layout**: `packages/mobile/` is a standalone in-repo package (NOT an npm workspace — the repo root has no `workspaces` field, so its `node_modules` is fully isolated from the web/Electron tree). Expo Router under `src/app/`: `index`, `scan-qr`, `create-from-tag`, `settings`, `filament/[id]`; helpers under `src/lib/`: `api`, `serverConfig`, `nfc`, `zeroconf`, `writeQueue`, `pendingScan`, `features`, `types`, `base64`, `theme`. The original plan lives in `docs/mobile-app-plan.md`. **Always run Expo from `packages/mobile/` only** (see the iOS-dev-build memory note).
- **Scanning**: QR/label scanning (`expo-camera`) resolves an `instanceId` via `GET /api/filaments/match?instanceId=…`, or a spool deep link's `?spool=<id>` via `GET /api/spools/{spoolId}`. NFC (`react-native-nfc-manager`) reads OpenPrintTag (NFC-V/ISO 15693) tags and POSTs the raw bytes to `POST /api/nfc/decode` for **server-side decode** — the phone does no CBOR/NDEF parsing. (Bambu MIFARE Classic is Android-only — iPhones can't read it.)
- **NFC feature gate**: `EXPO_PUBLIC_ENABLE_NFC` (mirrored in `src/lib/features.ts` as `NFC_ENABLED`, default on; `=0` produces a QR-only build for a free Apple ID that can't get the Core NFC entitlement — the NFC UI entry points hide so the build looks intentional, not broken).
- **Server config** (`src/lib/serverConfig.tsx`): the base URL + optional API key persist in `expo-secure-store`. The address is set manually OR auto-discovered via mDNS (`src/lib/zeroconf.ts`, `react-native-zeroconf` — gracefully no-ops with `supported: false` on web / Expo Go). When the server runs `FILAMENTDB_API_KEY`, the client sends `Authorization: Bearer <key>` on every request (harmless when the server is unauthenticated).
- **Create-from-tag** (`src/app/create-from-tag.tsx` + `api.createFromTag`): POSTs `{ tagData, overrides, spoolRemainingGrams }` to `POST /api/filaments`; the server maps the decoded tag → filament payload, the user's confirmed name/vendor/type override, and `spoolRemainingGrams` (null = catalog-only, no spool).
- **Per-spool updates**: move location, set remaining weight, retire/un-retire (`api.updateSpool` → `PUT …/spools/{spoolId}`), plus usage logging (`api.logUsage`) and dry-cycle logging (`api.logDryCycle`).
- **Offline write queue** (`src/lib/writeQueue.ts`): persists mutations in `AsyncStorage` and replays them FIFO when the server is reachable again — survives app restart, capped at 200 (oldest dropped first). **Only idempotent absolute-SET ops are queued** (`updateSpool` — weight/location/retire); `logUsage`/`logDryCycle` DECREMENT/APPEND so replaying a committed-but-lost response would double-apply — they require live connectivity and are never queued. A 4xx/5xx (real rejection) is surfaced/dropped, not queued; only network failures (`ApiError` status 0) queue.
- **Build & distribution (EAS, NOT Xcode Cloud)**: managed Expo / Continuous Native Generation — `ios/` and `android/` are generated by `expo prebuild` and **never committed** (gitignored), so Xcode Cloud has no Xcode project to build. Builds go through **EAS Build** instead (`packages/mobile/eas.json` — `preview` / `preview-qr` / `production` profiles; `preview-qr` sets `EXPO_PUBLIC_ENABLE_NFC=0` for a no-NFC, free-Apple-ID-signable build; `production` is `appVersionSource: remote` + `autoIncrement`). A repo-root `.easignore` scopes the upload to `packages/mobile` (EAS archives the git root by default), restating the secret/local excludes since `.easignore` replaces `.gitignore` for EAS. The `eas-build-mobile.yml` workflow (manual, needs `EXPO_TOKEN`) queues a cloud build; one-time `eas login`/`eas init` + an interactive iOS build to set up signing (the App ID needs the NFC Tag Reading capability + a paid account for an NFC build) are owner steps. Local dev stays on `expo run:ios`.

Note: PC/SC's `SCARD_STATE_PRESENT` bit can fire spuriously (driver-dependent — observed on ACS readers, especially the ACR1552U on macOS). The reader-status handler in `electron/nfc-service.ts` skips the FIRST event per reader to dodge the documented plug-in phantom (GH #230), but a later event with `SCARD_STATE_CHANGED` toggled can still set `tagPresent: true` without a real tag in the field. Without the corrective `tagPresent` clear, the renderer pill stays at "Tag detected" indefinitely and survives unplug+replug. The same first-event skip also drops a tag *already resting* on the reader at connect time (it produces no later state-change event); #572 handles that by emitting `presentAtConnect` on the skipped present event for a one-shot silent verification read — see the "v1.34.8–1.34.10 Features" section.
